### 引擎挂进界面的那一段（新增，必须理解）

```
合同文本
 → contractFacts.extractContractFacts   六字段初值（月租/押金/租期/城市/类型）
 → contractReview.analyzeContract        findings（level: high/medium/low）
 → riskMapper.toRiskModel                九件套：
        levelFromSeverity  high→必须改；high+AI 推断→建议确认；medium/low→仅提醒
        categoryOf         条款类别（押金/提前退租/维修/水电/租金调整/…）
        AMOUNT_KEY_BY_CAT  只有能算成钱的类别才挂金额键，其余留 null（显示「机制」不编数字）
        locationOf         条文号 + 页码 + 行号
        scriptFor          两档话术（礼貌版 / 协商版）+ 三种回法
 → amountEngine.computeWorstCase        同一金额键只算一次，避免三条风险各赔一遍违约金
 → describeDegradation                  降级：failed / partial / ok(带 noSuggestion)
```

**这条链的硬规则**：`riskMapper` 只能"翻译"，不能"发明"。引擎没命中就不该凭空造一条风险；金额键映射不上就显示「机制」，不许估一个数。`tests/unit/risk-mapper.test.mjs` 与 `amount-engine.test.mjs` 就是守这两条线。

### 数据模型：`Risk`（九件套）

```js
Risk = {
  id, level: 'must' | 'check' | 'note',   // 必须改 / 建议确认 / 仅提醒
  cat, title, consequence,                // 类别、标题、这条会怎么坑我
  original, suggestion,                   // 原句、建议改为
  law: { name, version, scope, url },     // 法律依据（无依据不出结论）
  location: { article, page, line, sentence },
  amountKey: 'depositDeduct' | 'termination' | 'repair' | 'utility' | 'rentHike' | null,
  confidence: '高' | '中' | '待核对',
  scripts: { polite, firm },              // 两档话术
  objections: [{ q, a }],                 // 房东三种回法 + 怎么接
  hasSuggestion: boolean,
}
```

## 一、一页速览

| 维度 | 现状 | 一句话理由 |
|---|---|---|
| 交付形态 | Web 单页应用 + 同进程 API 服务 | 一个人维护，不做前后端分离部署 |
| 前端 | React 19 + Vite 8（纯 JS/JSX，无 TS） | 构建快、改一版就能跑，AI 改起来上下文小 |
| 样式 | 手写 CSS（`index.css` + `App.css`），无 UI 框架 | 界面是产品差异点，不想被组件库锁死 |
| 后端 | Express 5（ESM `.mjs`）单进程 | 除模型代理外无重逻辑，单进程足够 |
| 模型接入 | OpenAI 兼容 Chat Completions 协议，服务端代理 9 家供应商 | 换模型只改环境变量，前端不用动 |
| 审查引擎 | 本地规则引擎（2288 行）+ 大模型 + 本地检索 RAG | 规则保底、模型补漏，断网也能出结论 |
| 文档解析 | mammoth（docx）/ pdfjs-dist（pdf）/ 三级 OCR | 用户手里是纸质合同照片和 PDF |
| 数据存储 | 无数据库：前端 localStorage + 服务端 Redis(可选)/内存 | 合同是敏感数据，"不落库"本身就是卖点 |
| 测试 | Node 原生断言单测 + Playwright e2e + 脚本化评测 | 规则库改动频繁，必须有回归网 |
| 部署 | 单端口（API + 静态托管同源）/ Render / Docker | 免跨域、免 Nginx、免运维 |

代码体量（`wc -l` 实测）：

- 前端 `app/src`：**11,952 行**（JS/JSX）+ **9,494 行 CSS**。单文件前三：`App.css` 9,446 行、`features/contractReview.js` 2,288 行、`App.jsx` 1,882 行。
- 服务端 `app/server`：**4,444 行**（`.mjs`），其中法律知识库 836 行、小程序编排 407 行。
- 测试：`tests/unit` 17 个文件、`tests/e2e` 5 个 spec / 29 条用例；`package.json` 共 27 条 npm 脚本。
- 规则库：`contractReview.js` 内 50 组 `makeLeaseFinding` 规则定义（覆盖 7 个主题分组、11 个评分维度）。

## 二、技术栈说明

### 2.1 前端栈

| 依赖 | 版本 | 用途 | 为什么是它 / 什么时候该换 |
|---|---|---|---|
| react / react-dom | 19.2.6 | 视图层 | 状态耦合在一条长流程里（导入→审查→采纳→导出），组件化最省事。页面再多也不需要 Next.js（无 SEO、无服务端渲染需求） |
| vite | 8.0.12 | 开发服务器 + 构建 | 冷启动秒级；`/api` 代理到 8787 一行配置解决开发期跨域 |
| @vitejs/plugin-react | 6.0.1 | JSX 编译 | 默认即可 |
| lucide-react | 1.21.0 | 图标 | 按需引入、无字体文件，避免图标字体拖慢首屏 |
| mammoth | 1.12.0 | DOCX 转文本 | 纯 JS、浏览器与服务端都能跑，比 `docx` 更适合"读"；`docx` 只用于"写" |
| pdfjs-dist | 6.2.108 | PDF 抽文本 | 租房合同大量是 PDF；需注意它要单独配 worker |
| tesseract.js + chi_sim/eng 数据 | 7.0.0 | 浏览器端离线 OCR | 前端兜底，服务端不可用时仍能识别图片合同 |
| docx | 9.7.1 | 生成审查报告 / 修订合同 | 用户要的是能发给房东的文件，不是网页截图 |

没有引入的东西，以及不引入的理由：

- **TypeScript**：当前无类型系统，靠约定 + 单测。收益真实存在（`Finding` 有 13 个字段），但迁移成本高于现阶段收益，见 6.4 的低成本替代方案。
- **Tailwind / Ant Design**：样式全部手写在两个 CSS 文件里，视觉是产品叙事的一部分（"像一份正式报告"），组件库会把它拉回"后台管理风"。
- **状态管理库（Redux/Zustand）**：跨模块共享的状态只有"当前合同 + 当前审查结果"，`App.jsx` 用 `useState` + props 透传足够；真正的问题是 `App.jsx` 太大，而不是缺状态库（见第八章）。
- **路由库**：模块切换用 `activeTab` 状态实现，不需要 URL 路由。若要做"分享审查结果链接"，才需要引入。

### 2.2 后端栈

| 依赖 | 版本 | 用途 |
|---|---|---|
| express | 5.2.1 | HTTP 服务、路由、静态托管、SPA fallback |
| cors | 2.8.5 | 开发期白名单来源校验（生产走同源，几乎不触发） |
| multer | 2.2.0 | 合同文件 / 图片上传，内存存储，单文件 8MB |
| dotenv | 17.4.2 | 本地读取 `.env` |
| 智谱视觉 API | — | OCR 第一级（质量最好，需 `ZHIPU_API_KEY`） |
| RapidOCR（`rapidocr-image.py`） | — | OCR 第二级，本地 Python 进程 |
| Tesseract.js | 7.0.0 | OCR 第三级，纯 JS 兜底 |

服务端不依赖任何数据库驱动。额度与幂等记录走 `usage-store` 抽象：配了 Upstash Redis REST 就持久化，没配就用进程内 Map（重启即清空，只适合演示）。

| OpenAI-compatible | `api.openai.com/v1` | `gpt-4.1-mini` | `OPENAI_API_KEY` → `AI_PROXY_API_KEY` |
| 通义千问 | `dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` | `DASHSCOPE_API_KEY` → `QWEN_API_KEY` |
| 智谱 GLM | `open.bigmodel.cn/api/paas/v4` | `glm-4-flash` | `ZHIPU_API_KEY` → `BIGMODEL_API_KEY` |
| Moonshot | `api.moonshot.cn/v1` | `moonshot-v1-8k` | `MOONSHOT_API_KEY` |
| 百川智能 | `api.baichuan-ai.com/v1` | `Baichuan4` | `BAICHUAN_API_KEY` |
| 腾讯混元 | `api.hunyuan.cloud.tencent.com/v1` | `hunyuan-lite` | `HUNYUAN_API_KEY` → `TENCENT_HUNYUAN_API_KEY` |
| 火山方舟 / 豆包 | `ark.cn-beijing.volces.com/api/v3` | `doubao-1-5-lite-32k-250115` | `ARK_API_KEY` → `VOLCENGINE_API_KEY` |
| MiniMax | `api.minimax.chat/v1` | `MiniMax-Text-01` | `MINIMAX_API_KEY` |

智谱另有独立视觉链路（`zhipuVisionApiKey` / `zhipuVisionModels`），只负责图片 OCR，不参与对话。

关键约束（已实现，改动时不要破坏）：

1. **密钥只在服务端**。前端没有任何 Key 输入框，`.env.example` 里明确写了"访问用户不会看到也不需要填写 API Key"。
2. **上游地址不可被客户端指定**。`AI_PROXY_ALLOW_CUSTOM_UPSTREAM` / `AI_PROXY_ALLOW_CLIENT_BASE_URL` 默认 `false`，否则代理会变成任意 URL 转发器（SSRF 风险）。
3. **超时与取消**：`AI_PROXY_TIMEOUT_MS`（默认 45s）、`OCR_TIMEOUT_MS`（默认 90s），并由服务端夹在安全区间内；客户端断开时上游请求同步中止。

### 2.5 部署栈

三条路径，共用同一份代码：

| 方式 | 文件 | 实际状态 |
|---|---|---|
| 本地双进程 | `npm run dev:full` | 可用（Vite 5173 + 代理 8787） |
| Render（生产） | `render.yaml` | 可用：`npm install && npm run build` → `npm start`，健康检查 `/api/health` |
| Docker | `Dockerfile` | **当前不可用**，缺 `npm run build` 与 `dist` 拷贝，详见第八章 P1-1 |

生产形态是**单端口**：`ai-proxy.mjs` 同时提供 `/api/*` 和 `dist` 静态资源，非 `/api` 路径回落到 `index.html`。好处是零跨域配置、零反向代理，坏处是前后端无法独立扩缩容——以当前流量这不是问题。

### 3.2 依赖方向（硬规则）

```
前端：  constants → utils → features → components → App.jsx
服务端：config → lib → services → routes → ai-proxy
```

两条链都是**单向**，无循环引用。违反这条规则的改动会立刻体现在构建或运行时报错，而不是三个月后。

唯一的例外需要明确记住：**服务端反向引用了两个前端纯函数**——

- `server/evaluate-advisor*.mjs` → `src/features/negotiationAi.js`、`src/utils/privacy.js`
- `server/subsidy-policy-service.mjs` → `src/data/subsidyPolicies.js`

这些是"前后端共享的纯逻辑/静态数据"，不是双向依赖（那两个文件夹不 import 任何 `server/` 代码）。但这解释了 `Dockerfile` 里为什么单独 `COPY src/data`——如果继续共享，Dockerfile 需要跟着补 `src/features`、`src/utils`。

### 3.3 一次审查请求的完整链路

```
用户粘贴/上传合同
   → utils/fileImport.js        按扩展名分派：txt/md 直读、docx 走 mammoth、pdf 走 pdfjs、图片走 OCR
   → features/contractReview.js cleanContractTextForReview   去页眉页脚、断行、空格噪声
   → analyzeContract(text, profile)                          本地规则引擎出 findings（离线可用）
   → features/aiAssistant.js    createAiReviewPrompt + buildRagContextPrompt
   → POST /api/ai/chat          服务端限流 → 额度 → 脱敏日志 → 上游调用（超时/取消）
   → normalizeAiFindings        逐字证据校验：AI 给的原文片段必须能在合同里找到，否则丢弃
   → mergeFindings              本地 ∪ AI 去重，enrichFindingsWithLegalBasis 补法条
   → getRiskSummary / getDimensionScores                     总分、等级、11 个维度分
   → 界面风险清单（按主题分组、按 P0/P1/P2 排序）
   → applyRevisionItem          采纳替换条款 → createRevisedContractDraft
   → utils/docxExport.js        导出修订合同 / 审查报告
   → 二次复查：修改后的合同重新走一遍上面链路，验证风险是否消失
```

"断网可演示"落在这条链路的两处：本地规则引擎（第 3 步）和 `createLocalAiFallbackReply`（AI 失败兜底）。

## 六、数据模型设计

原则：**没有数据库，但模型必须显式**。所有跨层传递的数据都在这里定义，字段名就是契约。

### 6.1 审查域（核心）

```js
/** 审查配置 */
ReviewProfile = {
  contractType: 'auto' | 'lease' | 'service' | 'purchase' | 'employment' | 'cooperation',  // 默认 lease，'auto' 走信号词识别
  partyRole:    'partyB',                                    // 站在乙方（租客）视角
  reviewDepth:  'strict' | 'standard',                       // 默认 strict
}

/** 一条风险（系统的原子单位，13 个字段） */
Finding = {
  id:           string,        // 'lease-arbitrary-deposit-deduction'，稳定标识，用于法条映射/测试/去重
  title:        string,        // '押金扣款项目过宽'
  level:        'high' | 'medium' | 'low',
  score:        number,        // 风险分，参与总分计算
  dimension:    string,        // 11 个维度之一：租期/租金/押金/解除/维修/居住权/费用/违约责任/管辖/格式条款/权属
  priority:     'P0' | 'P1' | 'P2',
  keywords:     string[],      // 命中证据（必须来自合同原文，用于界面上做高亮）
  matchGroups:  string[][],    // 规则匹配：每组至少命中一个
  matchPredicate?: (text) => boolean,  // 复杂规则（共现、距离）用代码判定
  evidence:     string,        // 合同原文片段 —— 无证据不出结论
  explain:      string,        // 大白话：这条会怎么坑我
  suggestion:   string,        // 修改建议
  negotiation:  string,        // 跟房东怎么说
  replacement:  string,        // 可直接替换的条款文本
  legalBasis?:  string,        // 法规依据（由 legalBasisMap 补齐）
}

/** 审查结果摘要 */
RiskSummary = {
  score: number,               // 0-88（展示上限 88，含义"没有绝对安全"）
  level: 'high' | 'medium' | 'low' | 'safe',
  counts: { high, medium, low },
  dimensionScores: Record<dimension, number>,
}

/** 采纳后的替换项 */
RevisionItem = { findingId: string, replacement: string, appliedAt: number }
```

`level` 与 `priority` 是**双轨**：`level` 面向用户（高/中/低），`priority` 面向处理顺序（P0/P1/P2）。两套语义当前靠人工保持一致，这是潜在的漂移点，规范建议见 7.4。

### 6.2 决策域

```js
Needs   = { monthlyBudget, maxCommuteMinutes, moveInDate, leaseTermMonths, mustHaves[] }   // mustHaves ≤ 5
Listing = { listingName, city, monthlyRent, depositAmount, prepaidMonths, agencyFee,
            monthlyFixedFees, utilitiesEstimate, commuteMinutes, availableDate, listingText }

/** 字段级可信度：每个房源字段单独标注来源 */
Sources = Record<field, 'contract' | 'verbal' | 'guess'>
// 默认：租金/押金/预付月数=contract，中介费/固定费用/可入住日=verbal，通勤/水电=guess

DecisionResult = {
  key: 'incomplete' | 'pause' | 'confirm' | 'more-info' | 'go',
  tone: 'neutral' | 'danger' | 'warning' | 'safe',
  title, subtitle,    // 直接可展示的结论文案
}
```

决策顺序（`resolveDecision` 的判定优先级，改动时不要调换）：

```
未填完 → incomplete
预算冲突 → pause（一票否决）
存在 1 条以上高风险 → confirm
关键信息缺失 → more-info
其余 → go
```

`sources` 是产品主张"合同 > 口头 > 猜测"的数据化落地：同一个租金，标 `contract` 和标 `guess` 会让结论不同。

### 6.3 本地持久化（浏览器）

| localStorage key | 内容 | 清空方式 |
|---|---|---|
| `signahead-history` | 审查历史记录 | 界面"清除全部痕迹" |
| `signahead-ai-config` | 模型偏好（不含密钥） | 同上 |
| `signahead-ai-feedback` | 每条 AI 回答的反馈 | 同上 |
| `signahead-local-only-mode` | 纯本地模式开关（不走任何外网） | 同上 |
| `signahead-account-id` | 浏览器生成的匿名身份（额度归属） | 同上 |
| `signahead-negotiation-session` | 谈判会话快照（合同文本、已采纳项、对话） | 同上 |

一条硬约束：**这些数据不上传服务端**。合同文本只在单次请求内存在，服务端日志走字段白名单，不写合同内容。

### 6.4 服务端状态

```js
UsageRecord = { ownerId, date, count, idempotencyKeys[] }   // Redis REST 或进程内 Map
```

没有用户表、没有合同表、没有审查结果表。这是刻意设计：**"不存储"是可验证的信任承诺**，也是竞品分析里 LeaseSnipe 验证过的路径。

### 6.5 无类型系统的补偿方案

在引入 TS 之前，建议用 JSDoc typedef 在 `features/` 顶部声明上述模型，配合 ESLint `valid-jsdoc` 或 `checkJs`，成本不到半天，收益是 IDE 能提示 13 个字段的拼写。这是投入产出比最高的一步。

## 七、代码规范建议

### 7.1 已经成立、必须保持的约定

| 约定 | 现状 | 检查方式 |
|---|---|---|
| 命名：组件 `PascalCase.jsx`，逻辑 `camelCase.js`，服务端 `kebab-case.mjs` | 全仓库一致 | 人眼 |
| 服务端依赖单向 `config → lib → services → routes` | 已成立 | 构建/运行即报错 |
| `features/` 不 import React、不发请求 | 已成立 | 单测能跑即证明 |
| 密钥只在服务端，前端零 Key | 已成立 | 全局搜 `API_KEY` 只应命中 `server/` |
| 风险必须有 `evidence` 且来自原文 | 已成立（`normalizeAiFindings` 逐字校验） | `ai-review-reliability.test.mjs` |
| 提交信息用 `feat/fix/refactor/docs/chore` 前缀 | 已成立（git log 可见） | — |

### 7.2 五条新增硬规则（建议写进 CONTRIBUTING 或 AI 提示）

1. **单文件 400 行红线**。超过必须拆。当前三个超标点（`App.css` 9,446、`contractReview.js` 2,288、`App.jsx` 1,882）是例外，只允许缩、不允许再长。
2. **`components/` 不得出现业务计算**。判断标准：如果一段代码能写成"输入 A 输出 B"的纯函数，它就该在 `features/`。
3. **`features/` 不得 import `components/`、不得直接 `fetch`**。所有网络调用经 `features/aiAssistant.js` 或容器层统一出口，否则断网兜底会漏。
4. **新增服务端能力先进 `services/`**，`routes/` 只做参数校验、守卫挂载、响应组装。
5. **新增规则必须带一条单测 + 一个埋雷样本**。规则库是产品资产，没有测试的规则等于没有规则。

### 7.3 拆分建议（针对三个超标文件）

`contractReview.js`（2,288 行）按规则主题拆成 `features/review/rules/`：

```
features/review/
├── index.js              # 对外只暴露 analyzeContract 等 4 个入口
├── engine.js             # 匹配、评分、去重（与规则内容无关）
├── rules/deposit.js      # 押金与退租扣款（5 条）
├── rules/lateFee.js      # 逾期与强制催收（6 条）
├── rules/maintenance.js  # 维修与自然损耗（3 条）
├── rules/occupancy.js    # 居住权与访客（4 条）
├── rules/termination.js  # 提前解约与续租（3 条）
├── rules/fees.js         # 费用与税费（3 条）
├── rules/validity.js     # 合同效力与争议（3 条）
└── text.js               # 清洗、条款提取
```

拆分时保持 `analyzeContract` 签名不变，`tests/unit` 的 17 个文件全部通过即为安全。这一步的收益是：以后加规则只改一个 200 行的文件，AI 改代码时的上下文也小一个数量级。

`App.jsx`（1,882 行）抽 4 个自定义 hook：

| hook | 接管 |
|---|---|
| `useContractReview` | 导入、清洗、审查、结果与阶段状态 |
| `useNegotiation` | 采纳、谈判会话、对话、快照恢复 |
| `useDecisionInputs` | needs / listing / sources 与校验 |
| `useAiAssistant` | 消息、发送、额度、反馈 |

`App.jsx` 最终保留"拼装 + 布局"，目标 400 行内。

`App.css`（9,446 行）按"页面 → 区块 → 组件"切三个层级，用 CSS `@layer` 声明顺序，避免拆完以后选择器互相覆盖：

```
styles/
├── tokens.css        /* 颜色、字号、间距、圆角、阴影（唯一的硬编码来源） */
├── base.css          /* reset、排版、滚动条 */
├── layout.css        /* 顶栏、侧栏、内容区框架 */
├── pages/            /* proposal / review / negotiation / decision 各一文件 */
├── components/       /* review-card / risk-badge / finding-list / assistant … */
└── index.css         /* 只做 @layer 声明与 @import 汇总 */
```

拆分判据：一个文件对应一个页面的主内容区，或一个组件；超过 300 行说明这个组件该继续往下拆。**先做 JS 拆分再做 CSS**——JS 定下来以后，组件的类名边界才稳定，否则会拆两遍。

### 7.4 术语与一致性

- `level`（高/中/低）与 `priority`（P0/P1/P2）必须同步维护，建议在 `constants/` 放一张显式映射表 `LEVEL_TO_PRIORITY`，规则定义时引用它而非手写两个字面量。
- 风险 `id` 一旦发布不得改名（法条映射、测试用例、历史记录都按 id 关联）。要改语义，新增 id 并保留旧 id 的兼容映射。
- 面向用户的文案（`explain` / `negotiation`）统一第二人称、短句、不用法律术语堆砌。`review-ui.test.mjs` 这类测试实际在守这条线，新增文案时别绕过。

### 7.5 给 AI 派活时的写法（本项目实测有效）

```
范围：只改 app/src/features/review/rules/deposit.js 与对应单测，不动其它文件
约束：analyzeContract 签名不变；新 Finding 必须含 evidence 且证据来自原文；
      level 与 priority 用 constants 里的映射；不引入新依赖
验收：node tests/unit/contract-review-playbook.test.mjs 全绿；npm run build 通过
```

把"范围 + 约束 + 验收命令"三件事写清楚，比描述需求细节更能减少返工。

| **P1** | `Dockerfile` 构建出的镜像无法提供前端页面 | 镜像只 `COPY server` 和 `src/data`，未 `RUN npm run build`、未 `COPY dist`；而 `config.mjs` 的 `distDir` 指向 `app/dist`，`.dockerignore` 还显式忽略了 `dist`。容器内 `indexHtmlPath` 不存在 → 走 404 分支返回 "Frontend build not found" | 改成两阶段构建：`builder` 阶段 `npm ci && npm run build`，`runner` 阶段 `COPY --from=builder /app/dist ./dist`；或直接删掉 Dockerfile，只保留 Render |

## 九、演进路线（按触发条件，而不是按时间）

个人项目最大的风险不是"架构不够先进"，而是"提前上了用不上的东西"。下面每一条都绑定一个可观测的触发条件：

| 能力 | 现在要不要 | 触发条件 | 上了之后改哪里 |
|---|---|---|---|
| TypeScript | 不要 | 团队 > 1 人，或 Finding 字段连续两次因拼写出错 | 增量迁移：`features/` 先转 `.ts`，Vite 原生支持 |
| 数据库（Postgres） | 不要 | 需要跨设备同步审查历史，或做付费订阅 | 只加 `users` / `reviews` 两张表；合同正文仍不落库 |
| 向量检索（pgvector/Qdrant） | 不要 | 本地 n-gram 检索的 Top-5 命中率低于 70%，且知识条目 > 2,000 | 只替换 `rag-engine.mjs`，接口 `search(query, limit)` 不变 |
| 任务队列 | 不要 | 单次审查耗时 > 60s 需要异步化，或并发 > 20 | 长审查改"提交任务 + 轮询"，前端已有 `reviewStage` 状态机可复用 |
| 登录体系 | 不要 | 有付费意愿用户，或需要跨端额度 | 先接微信/手机号，替换 `signahead-account-id` |
| 正式组件库 | 不要 | 界面需要 3 人以上协作维护 | 只替换 `components/` 原子层，`features/` 不受影响 |
| 小程序端 | 已有服务端骨架 | 小程序工程重新进仓库时 | 复用 `/api/miniapp/*`，前端另建 `miniapp/` |

一句话版本：**当前架构的扩展点已经留好了**（模型可换、规则可加、检索可换、部署可换），缺的不是更多技术，而是把两个大文件拆开。

## 十、新接手者的上手顺序

1. 读 `README.md`（工作区分层）→ `app/README.md`（产品主线与演示路径）。
2. 跑起来：`cd app && npm install && npm run dev:full`，先用演示合同走一遍"审查 → 采纳 → 导出 → 复查"。
3. 读 `src/features/contractReview.js` 里 `lease-arbitrary-deposit-deduction` 这一条规则（本章 6.1 有节选），理解 13 个字段怎么协作。
4. 读 `server/ai-proxy.mjs`（83 行）→ `routes/ai.mjs`（174 行），理解一次 AI 调用经过哪些守卫。
5. 改一条规则，跑 `node tests/unit/contract-review-playbook.test.mjs` 与 `npm run build`，确认闭环。
