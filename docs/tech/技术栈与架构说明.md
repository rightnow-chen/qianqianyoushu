## 一、一页速览

| 维度 | 现状 | 一句话理由 |
|---|---|---|
| 交付形态 | 5 屏 + 5 Tab 单页应用（hash 路由），前端与 API 同进程部署 | 一个人维护，不做前后端分离 |
| 前端 | React 19.2 + Vite 8（纯 JS/JSX，无 TS） | 构建快、改一版就能跑，AI 改动的上下文小 |
| 样式 | 手写 CSS：`styles/tokens.css`（49 行）+ `styles/app.css`（2,668 行） | 界面是产品差异点，不想被组件库拉回"后台风" |
| 后端 | Express 5（ESM `.mjs`）单进程，装配入口 83 行 | 除模型代理与 OCR 外无重逻辑 |
| 模型接入 | OpenAI 兼容 `/chat/completions`，9 家供应商预设 | 换模型只改环境变量，前端零改动 |
| 审查引擎 | 本地规则引擎（`contractReview.js` 2,288 行）+ 大模型补漏 + 本地检索 | 规则保底，断网也能出结论 |
| 文档解析 | mammoth（docx）/ pdfjs legacy（pdf）/ 三级 OCR | 用户手里是合同照片和 PDF |
| 数据存储 | **零存储**：前端不写 localStorage，服务端不落库 | 合同是敏感数据，"不存储"本身是信任卖点 |
| 测试 | 15 个单测文件（`test:unit` 串了其中 14 个）+ 20 步 e2e 主路径 + 脚本化评测 | 规则库改动频繁，必须有回归网 |
| 部署 | 单端口（API + 静态托管同源）/ Render 可用 / Docker 待修 | 免跨域、免 Nginx、免运维 |

## 二、技术栈说明

### 2.1 前端栈

| 依赖 | 版本 | 用途 | 为什么是它 / 什么时候该换 |
|---|---|---|---|
| react / react-dom | 19.2.6 | 视图层 | 一条长流程（上传→确认→分析→工作台），组件化最省事。无 SEO 需求，不需要 Next.js |
| vite | 8.0.12 | 开发服务器 + 构建 | 冷启动秒级；`/api` 代理一行解决开发期跨域 |
| @vitejs/plugin-react | 6.0.1 | JSX 编译 | 默认即可 |
| lucide-react | 1.21.0 | 图标 | 按需引入、无字体文件 |
| mammoth | 1.12.0 | DOCX → 文本 / 段落层级 | 纯 JS，浏览器与服务端都能跑；它给的是"读"，写交给 `docx` |
| pdfjs-dist | 6.2.108 | PDF 抽文本 + 渲染原件 | 租房合同大量是 PDF。**必须用 `legacy/build`**，见 2.6 坑位 |
| tesseract.js + chi_sim/eng | 7.0.0 | 浏览器端离线 OCR | 服务端不可用时仍能识别图片合同 |
| docx | 9.7.1 | 生成修订版 / 批注版合同 | 用户要的是能发给房东的文件，不是网页截图 |

**没有引入的东西，以及不引入的理由：**

- **TypeScript**：`Risk` 有 15 个字段、`Finding` 有 13 个，确实需要约束；但当前靠单测 + JSDoc 能撑住，迁移成本高于收益。低成本替代见 6.6。
- **Tailwind / 组件库**：全部样式手写在两个 CSS 文件里。视觉是产品叙事的一部分（"像一份正式报告"），组件库会把它拉回通用后台风。
- **状态管理库**：跨屏共享的只有 `session` 一个对象，`App.jsx` 用 `useState` 足够。真问题是"状态之间的派生关系"，不是"缺库"。
- **路由库**：5 屏 + 5 Tab 用 `window.location.hash` 手写实现（`readRoute` / `routeToHash`），共 30 行。需要"分享审查结果链接"这种带状态的深链时才考虑引入。

### 2.2 后端栈

| 依赖 | 版本 | 用途 |
|---|---|---|
| express | 5.2.1 | HTTP 服务、路由、静态托管、SPA fallback |
| cors | 2.8.5 | 来源白名单（生产同源，几乎不触发） |
| multer | 2.2.0 | 合同文件 / 图片上传，内存存储，单文件 8MB |
| dotenv | 17.4.2 | 本地读取 `.env` |
| 智谱视觉 API | — | OCR 第一级（质量最好，需 `ZHIPU_API_KEY`） |
| RapidOCR（`rapidocr-image.py`） | — | OCR 第二级，本地 Python 子进程 |
| Tesseract.js | 7.0.0 | OCR 第三级，纯 JS 兜底 |

服务端**不依赖任何数据库驱动**。额度与幂等记录走 `lib/usage-store.mjs` 抽象：配了 Upstash Redis REST 就持久化，没配就用进程内 Map（重启即清，只适合演示）。

| 智谱 GLM | `open.bigmodel.cn/api/paas/v4` | `glm-4-flash` | `ZHIPU_API_KEY` → `BIGMODEL_API_KEY` |
| Moonshot | `api.moonshot.cn/v1` | `moonshot-v1-8k` | `MOONSHOT_API_KEY` |
| 百川智能 | `api.baichuan-ai.com/v1` | `Baichuan4` | `BAICHUAN_API_KEY` |
| 腾讯混元 | `api.hunyuan.cloud.tencent.com/v1` | `hunyuan-lite` | `HUNYUAN_API_KEY` |
| 火山方舟 / 豆包 | `ark.cn-beijing.volces.com/api/v3` | `doubao-1-5-lite-32k-250115` | `ARK_API_KEY` |
| MiniMax | `api.minimax.chat/v1` | `MiniMax-Text-01` | `MINIMAX_API_KEY` |

智谱另有独立视觉链路（`zhipuVisionApiKey` / `zhipuVisionModels`），只做图片 OCR，不参与对话。

**三条已实现、改动时不能破坏的约束：**

1. **密钥只在服务端**。前端没有任何 Key 输入框，`.env.example` 明确写了"访问用户不会看到也不需要填写 API Key"。
2. **上游地址不可由客户端指定**。`AI_PROXY_ALLOW_CUSTOM_UPSTREAM` / `AI_PROXY_ALLOW_CLIENT_BASE_URL` 默认 `false`，否则代理会退化成任意 URL 转发器（SSRF）。
3. **超时与取消**：`AI_PROXY_TIMEOUT_MS`（45s）、`OCR_TIMEOUT_MS`（90s），由服务端夹在安全区间内；客户端断开时上游请求同步中止。

### 2.5 部署

| 方式 | 文件 | 状态 |
|---|---|---|
| 本地双进程 | `npm run dev:full` | 可用（Vite 5173 + 代理 8787） |
| 本地单端口 | `npm run build` → `npm start` | 可用：8787 同时给页面和 `/api` |
| Render | `render.yaml` | 可用：`npm install && npm run build` → `npm start`，健康检查 `/api/health` |
| Docker | `Dockerfile` | **不可用**，缺 build 与 dist 拷贝，见 8.1 |

生产形态是**单端口**：`ai-proxy.mjs` 同时提供 `/api/*` 和 `dist` 静态资源，非 `/api` 路径回落到 `index.html`。零跨域、零反向代理；代价是前后端无法独立扩缩容——当前流量不是问题。

### 2.6 踩过的坑（改代码前必读）

| 坑 | 现象 | 结论 |
|---|---|---|
| `pdfjs-dist` 用标准构建 | 旧内核（360 / QQ / 微信内置 / 旧 Edge）上传 PDF 直接报 `hashOriginal.toHex is not a function` | 必须用 `pdfjs-dist/legacy/build/*`，worker 从 1.6MB 变 2.4MB，**不要为省体积改回去**。`contract-import.test.mjs` 第 5–7 组钉死三处引用 |
| `PDFDocumentProxy` 没有 `destroy()` | 调错会在 React 卸载阶段抛 TypeError → 整页白屏 | 释放 worker 要调 `getDocument()` 返回的 `loadingTask.destroy()`；`PDFDocumentProxy` 只有 `cleanup()`。e2e 第 16 步守门 |
| docx@9.7 没有修订痕迹 API | 想做 Word 的 `w:ins/w:del` 追踪修改，库不提供 | 修订版实现为"已采纳替换 + 红色下划线 + 文末修改清单"；批注版用原生 Word 批注。见 `docs/tech/导出实现说明_合同docx.md` |
| 合同金额写 `4,500 元` | 用 `\d+` 会读成 500 | `AMOUNT_RE` 必须是 `\d[\d,]*`；"万元"要换算成元。`contract-facts.test.mjs` 守这条 |
| OCR 把千分位读成点 | "2,800元" 识别成 "2.800 元"，旧解析得 2.8 | `^\d{1,3}(?:\.\d{3})+$` 按千分位剥离；`1.2 万元` 不受影响 |
| tesseract worker 抛错 | `createWorker` 不传 `errorHandler`，库在 `process.nextTick` throw → 服务进程直接消失 | 必须传 `errorHandler` + `terminate().catch`；`ai-proxy.mjs` 另挂 `unhandledRejection` / `uncaughtException` 记日志不退出 |
| 静态服务器不认 `.mjs` | 上传 PDF 后"完全没反应" | `.mjs` 必须返回 `text/javascript`（pdf.js worker 是 `.mjs`）。线上部署同样要查 |
| `vite preview` 正服务 `dist` 时 `vite build` | 清 `dist/assets` 被拦，构建失败 | 先停 preview → `rm -rf dist` → build → 再起 preview |

### 3.2 五分钟看懂：一条主路径

```
#landing          首页 → 「选择文件」/「用演示合同」
   ↓
#upload           选文件 → 解析 → 质检（按来源分派语义）→ 不合格就拦
   ↓              PDF 看「文字来源 + 提取预览」；拍照才看「识别率 / 反光 / 重拍」
#confirm          六字段确认（月租 / 押金 / 租期 / 城市 / 房屋类型 / 出租人）
   ↓              读不到就是 0 并黄底高亮要求手填，不用默认值假装读到了
#analyzing        规则引擎 + AI 审查（模型 28 秒 / 用户体感 3 分钟，分步播报）
   ↓
#work?tab=ov      概览：结论 + 最坏合计 + 4 条必改摘要
     ?tab=risk    风险：9 条（3 必须改 / 2 建议确认 / 4 仅提醒），左栏原文高亮
     ?tab=fix     修改：逐条采纳 / 编辑后采纳 → 生成修订版 + 对比
     ?tab=say     话术：每类两档（礼貌版 / 协商版）+ 房东三种回法怎么接
     ?tab=check   待核实：8 件事（2 件已确认），合同内外一致性
   ↓
导出：修订版 DOCX / 批注版 DOCX（真下载，e2e 解包断言）
```

`route` 只有四个字段：`{ screen, tab, active, demo, mobile }`，全部进 URL hash。刷新不丢页面位置，也不存任何合同内容。

### 3.3 依赖方向（硬规则）

```
前端：  constants → utils → features → screens → App.jsx
服务端：config → lib → services → routes → ai-proxy
```

两条链都是单向，无循环引用。唯一的例外需要记住：**服务端反向引用了两个前端纯函数**——

- `server/evaluate-advisor*.mjs` → `src/features/negotiationAi.js`、`src/utils/privacy.js`
- `server/routes/health.mjs` 等 → 无（补贴那处反向引用已随模块删除，见第八章）

这些是"前后端共享的纯逻辑/静态数据"，不是双向依赖（那两个目录不 import 任何 `server/` 代码）。这也是 `Dockerfile` 里为什么单独 `COPY src/data`——但那个 Dockerfile 本身是坏的（8.1）。

### 3.4 引擎挂进界面的那一段（最该理解的一段）

```
合同文本
 → contractFacts.extractContractFacts   六字段初值（月租 / 押金 / 租期 / 城市 / 类型）
 → contractReview.analyzeContract        findings（level: high / medium / low）
 → riskMapper.toRiskModel                翻译成界面用的 Risk：
        levelFromSeverity   high→必须改；high 且 AI 推断→建议确认；medium/low→仅提醒
        categoryOf          9 类条款（押金 / 提前退租 / 维修 / 水电 / 租金调整 …）
        amountKeyOf         只有能算成钱的类别才挂金额键，其余留 null
        locationOf          条款号 + 页码 + 行号 + 句子
        scriptFor           两档话术 + 三种回法
 → amountEngine.computeWorstCase        同一金额键只算一次，避免三条风险各赔一遍违约金
 → describeDegradation                  降级：failed / partial / ok（含 noSuggestion）
```

**这条链的硬规则：`riskMapper` 只能"翻译"，不能"发明"。** 引擎没命中就不能凭空造一条风险；金额键映射不上就显示"机制"，不许估一个数。`tests/unit/risk-mapper.test.mjs` 与 `amount-engine.test.mjs` 就是守这两条线。

## 六、数据模型设计

原则：**没有数据库，但模型必须显式**。字段名就是跨层契约。

### 6.1 `Finding`（引擎输出，唯一事实源）

```js
Finding = {
  id:          string,        // 'lease-arbitrary-deposit-deduction'，稳定标识
  title:       string,        // '押金扣款项目过宽'
  level:       'high' | 'medium' | 'low',
  score:       number,        // 参与总分计算
  dimension:   string,        // 11 维：租期/租金/押金/解除/维修/居住权/费用/违约责任/管辖/格式条款/权属
  priority:    'P0' | 'P1' | 'P2',
  keywords:    string[],      // 命中证据（必须来自原文，用于高亮）
  matchGroups: string[][],    // 每组至少命中一个
  matchPredicate?: (text) => boolean,  // 复杂规则（共现/距离）用代码判定
  evidence:    string,        // 合同原文片段 —— 无证据不出结论
  explain:     string,        // 大白话：这条会怎么坑我
  suggestion:  string,        // 修改建议
  negotiation: string,        // 跟房东怎么说
  replacement: string,        // 可直接替换的条款文本
  legalBasis?: string,        // 法规依据（legalBasisMap 补）
  confidence?: 'confirmed' | 'verify' | 'inferred',
}
```

### 6.2 `Risk`（界面唯一认的模型，15 个字段）

```js
Risk = {
  id, level: 'must' | 'check' | 'note',   // 必须改 / 建议确认 / 仅提醒
  cat, catLabel,                           // 9 类条款
  severity: '高' | '中' | '低',            // 引擎原始严重度（给用户看的另一种口径）
  title,                                   // `${cat}：${title}`
  amountKey: 'depositDeduct' | 'termination' | 'repair' | 'utility' | 'rentHike' | null,
  location: { article, page, line, sentence },
  confidence: '高' | '中' | '待核对',
  consequence,                             // 这条会怎么坑我（会拼上金额）
  original, suggestion, why,
  law: { name, basis, url, verified },     // verified=false 时不显示"依据"字样
  scripts: { polite, firm, objections: [{ q, a }] },
  hasSuggestion: boolean,
  source: 'engine', score,
}
```

三个术语必须分清，别混用：

| 层 | 术语 | 值 |
|---|---|---|
| 引擎 | `level` | high / medium / low |
| 引擎 | `priority` | P0 / P1 / P2 |
| 界面 | `level` | must / check / note |

映射函数是 `levelFromSeverity(severity, confidence)`，只有一处。**降级规则**：`high` 但置信度是 `inferred` → 落到 `check`（规则不确定时不许吓人）；`medium` → `check`；`low` → `note`。

### 6.3 `session`（一次审查的全部上下文）

```js
session = {
  kind: 'empty' | 'real' | 'demo',
  fileName, fileSize, fileText, source,   // source: pdf / word / text / ocr / paste
  confidence: number | null,              // 只有 OCR 才有意义
  meta: { rent, deposit, months, city, type, landlord },  // 六字段，确认页产物
  facts,                                  // extractContractFacts 的原始输出
  quality: { mode, totalPages, pagesCountLabel, pages, checks, advice, footerHint, warn },
  rawFile: File | null,                   // 原件，确认页与结果页左栏要用
  structure: Array | null,                // Word 段落层级（还原排版）
  risks: Risk[],
  findings: Finding[],
  degradation: { status: 'ok' | 'partial' | 'failed', reason },
}
```

与 `session` 平行的三份交互态，都是 `{ [riskId]: value }` 形状：

- `done`：待核实清单的勾选
- `accepted`：已采纳的风险 id
- `edited`：采纳时用户改过的条款文本

### 6.4 金额口径

```js
AMOUNT_CONFIG = {
  depositDeductRate: 0.4,    // 押金扣款上限 = 押金 × 40%
  terminationMonths: 2,      // 退租违约金 = 月租 × 2
  repairEstimate: 3000,      // 大件维修单次估值
  utilityDeltaPerMonth: 180, // 商民用水电月差价
  rentHikeRate: 0.08,        // 年涨租上限 8%
}
```

**这五个数都是估值，不是法定值或统计值，界面每处必须标「估算」。** 金额由 `meta` 的月租 / 押金 / 租期算出，界面里不允许出现硬编码数字。

`amountForRisk` 的三种返回必须分开说：

| 情形 | 返回 | 界面 |
|---|---|---|
| 有月租/押金，能算 | `{ kind: 'loss', value }` | `¥3,200` |
| 没读到月租/押金 | `{ kind: 'missing' }` | "待补" + "补上就能算" |
| 条款本身无固定金额（按逾期天数） | `{ kind: 'none' }` | "没有固定金额，取决于真出事时怎么算" |

禁止出现 `−¥0` 或"多损失 ¥0"。`computeWorstCase` 用同一金额键只计一次，并用 `unpriced` 标记"算不出来"的部分。

### 6.5 质检模型

`qualityForFile(file, { source, text })` 按来源返回四套语义，**"识别率 / 反光 / 重拍 / 置信度"只对拍照 OCR 成立**：

| source | 说什么 | 不说什么 |
|---|---|---|
| pdf / word（`text`） | 文字层来源、提取了多少字、有没有串行 | 不提识别率、不提反光、不提重拍 |
| image（`ocr`） | 识别率、哪页不清楚、要不要补拍 | — |
| txt / paste（`plain`） | 读到多少字、是否完整 | 不编页数 |

规则在 `features/uploadQuality.js`，被 `tests/unit/upload-quality.test.mjs` 钉死（PDF / 纯文本两组断言不出现那四个词）。

### 6.6 存储：一个都不写

- **前端**：`src/` 全局没有任何 `localStorage` 调用（实测 `grep` 零结果）。勾选、采纳、编辑全部只在内存，刷新即清。
- **服务端**：不落库。只有额度与幂等记录进 `usage-store`（Redis REST 或进程内存），且不含合同内容。
- **日志**：`logger.mjs` 白名单字段输出，合同正文永不写日志。

这是产品主张的数据化落地，不是"还没做持久化"。

**无类型系统的补偿方案**：给 `Finding` / `Risk` / `session` 写 JSDoc typedef（`@typedef` + `@property`），配合 `checkJs` 或 ESLint，成本不到半天，IDE 就能提示 15 个字段的拼写。这是引入 TS 之前性价比最高的一步。

## 七、代码规范建议

### 7.1 已经成立、必须保持

| 约定 | 现状 | 怎么验证 |
|---|---|---|
| 命名：组件 `PascalCase.jsx`，逻辑 `camelCase.js`，服务端 `kebab-case.mjs` | 全仓库一致 | 人眼 |
| 服务端依赖单向 `config → lib → services → routes` | 成立 | 构建/运行即报错 |
| `features/` 不 import React、不发请求 | 成立 | 单测能跑即证明 |
| 密钥只在服务端 | 成立 | 全局搜 `API_KEY` 只命中 `server/` |
| 风险必须有 `evidence` 且来自原文 | 成立（`normalizeAiFindings` 逐字校验） | `ai-review-reliability.test.mjs` |
| 单文件不超过 400 行 | **守住了**：screens 最大是 `OriginalDoc.jsx` 296 行；唯一超标是规则库本体（2,288） | `find src -name "*.js*" -exec wc -l {} + \| sort -rn` |
| 提交信息用 `feat/fix/refactor/docs/chore` 前缀 | 成立 | `git log --oneline` |

### 7.2 五条硬规则

1. **`screens/` 里不写业务计算**。判断标准：能写成"输入 A 输出 B"的纯函数，就该进 `features/` 并有单测。
2. **`features/` 不得 import `screens/` 或 `components/`，不得直接 `fetch`**。网络出口统一在 `App.jsx`，否则断网兜底会漏。
3. **新增服务端能力先进 `services/`**，`routes/` 只做参数校验、守卫挂载、响应组装。
4. **新增规则必须带一条单测 + 一个埋雷样本**。规则库是产品资产，没测试的规则等于没规则。
5. **任何金额必须可追溯到 `AMOUNT_CONFIG` 或 `meta`**，界面出现硬编码数字即为 bug。

### 7.3 术语一致性

- 引擎说 `high/medium/low`，界面说 `must/check/note`，**映射只允许在 `riskModel.levelFromSeverity` 里发生一次**。
- 风险 `id` 一旦发布不得改名（法条映射、测试用例、历史都按 id 关联）。要改语义就新增 id。
- 面向用户的文案统一第二人称、短句、不用法律术语堆砌。`review-ui` 这类断言测试实际在守这条线。

### 7.4 还剩一个拆分工程

`contractReview.js` 2,288 行没拆，理由是它是规则库本体、每次改动都只碰其中一条。真要拆，按规则主题切成 `features/review/rules/`：

```
features/review/
├── index.js              # 对外只暴露 analyzeContract 等入口
├── engine.js             # 匹配、评分、去重（与规则内容无关）
├── rules/deposit.js      # 押金与退还（5 条）
├── rules/lateFee.js      # 逾期与强制催收（6 条）
├── rules/maintenance.js  # 维修与自然损耗（3 条）
├── rules/occupancy.js    # 居住权与访客（4 条）
├── rules/termination.js  # 提前解约与续租（3 条）
├── rules/fees.js         # 费用与税费（3 条）
├── rules/validity.js     # 合同效力与争议（3 条）
└── text.js               # 清洗、条款提取
```

拆分时保持 `analyzeContract` 签名不变，`npm run test:unit` 全绿即为安全（当前 14 条跑通）。

### 7.5 给 AI 派活的写法（本项目实测有效）


把"范围 + 约束 + 验收命令"写清楚，比描述需求细节更能减少返工。

## 八、已知问题与技术债

按严重度排序，全部经代码核对，不是猜测。

| 级别 | 问题 | 证据 | 建议 |
|---|---|---|---|
| **P1** | `Dockerfile` 构建出的镜像无法提供前端页面 | 只 `COPY server` 与 `src/data`，未 `RUN npm run build`、未 `COPY dist`；`.dockerignore` 还显式忽略 `dist`；`config.mjs` 的 `distDir` 指向 `app/dist` → 容器内 `indexHtmlPath` 不存在，落到 404 分支返回 "Frontend build not found" | 两阶段构建：builder 阶段 `npm ci && npm run build`，runner 阶段 `COPY --from=builder /app/dist ./dist`；或删掉 Dockerfile 只留 Render |
| **P2** | `contractReview.js` 2,288 行未拆 | 单文件占 features 层 39% | 见 7.4。不紧急（规则库本体），但新增规则时上下文会越来越贵 |
| **P3** | 6 个模块没有独立单测 | `scriptTemplates`（228）、`filePreview`（154）、`docHighlight`（129）、`officePreview`（111）、`reportText`（98）、`diff`（75） | 优先补 `diff`（纯函数，最好测）与 `scriptTemplates`（话术是卖点，错一个字用户就会照念） |

## 九、演进路线（按触发条件，不按时间）

个人项目最大的风险不是"架构不够先进"，而是"提前上了用不上的东西"。每条都绑一个可观测的触发条件：

| 能力 | 现在要不要 | 触发条件 | 改动范围 |
|---|---|---|---|
| TypeScript | 不要 | 团队 > 1 人，或 `Risk` 字段连续两次因拼写出错 | 增量迁移：`features/` 先转 `.ts`，Vite 原生支持 |
| 数据库 | 不要 | 需要跨设备同步审查记录，或做订阅 | 只加 `users` / `reviews` 两张表；合同正文仍不落库 |
| 向量检索 | 不要 | 本地 n-gram Top-5 命中率 < 70%，或知识条目 > 2,000 | 只换 `rag-engine.mjs`，接口 `search(query, limit)` 不变 |
| 任务队列 | 不要 | 单次审查 > 60s 需异步化，或并发 > 20 | 改"提交任务 + 轮询"，`AnalyzingScreen` 的进度机制可复用 |
| 登录体系 | 不要 | 有付费意愿用户，或需跨端额度 | 替换 Web 端匿名身份，服务端 `guards.mjs` 已有鉴权位 |
| 组件库 | 不要 | 界面需要 3 人协作维护 | 只换 `components/`，`features/` 不受影响 |
| 小程序端 | 服务端骨架已有 | 小程序工程重新进仓库 | 复用 `/api/miniapp/*`，另建 `miniapp/` |
| 城市差异化规则 | 不要（用户 11-08 明确） | 有真实武汉本地条款库 | 只扩 `contractReview` 的规则，不动结构 |

一句话：**扩展点都留好了**（模型可换、规则可加、检索可换、部署可换），缺的不是更多技术，而是把 P1 两个部署问题修掉。
