# 导出实现说明 · 合同 docx（修订版 / 批注版）

> 2026-11-08 ｜ 代码：`app/src/features/contractDocx.js`（533 行）｜ 单测：`app/tests/unit/contract-docx.test.mjs`（143 行）

## 一句话

**修订版** = 用户已采纳的修改替换进正文，替换处标红加下划线，文末附「改了什么」清单；
**批注版** = 正文一字不改，每条风险作为 Word 原生批注挂在对应的原句上。

## 为什么修订版不是 Word「修订痕迹」

Word 的 `w:ins / w:del`（接受/拒绝修订的绿红痕迹）在 `docx@9.7` 里没有公开 API，硬写 XML 会在不同 Word/WPS 版本上出现「痕迹不显示但文字已改」这种最难排查的错——文件看起来正常，房东打开却看不到改动。

所以修订版选了更笨但更可靠的做法：**直接替换文字 + 红色下划线标出**。好处是任何软件打开都能看见改了什么，不需要「接受修订」这一步；代价是它不可回退成一键「拒绝」。文末的修改清单把原文与改后文本逐条并排，等于把回退信息留在纸面上。

## 三个必须守住的口径

| 口径 | 做法 | 为什么 |
|---|---|---|
| 原文一字不动 | 定位时忽略空白（OCR 会把「标准由甲方核定」识别成「标 准 由 甲 方 核 定」），但**写进 docx 的字符来自原文切片**，不是归一化后的版本 | 归一化后再输出，等于把一份「不是你签过的那份合同」发给房东 |
| 定位不到就说定位不到 | 每条风险三种结果：`applied` / `not-accepted` / `not-found` / `overlap` / `no-change`，全部写进文末「未替换的条目」并说明原因 | 静默跳过最危险：用户以为 9 条都改了，实际只改了 6 条 |
| 批注挂原句 | 用 `CommentRangeStart / CommentRangeEnd / CommentReference`，批注正文四段：等级·类别 / 结论 / 建议改为 / 依据 | 房东在 Word 里点开批注就能看到「这句为什么有问题」，不用回头翻报告 |

## 数据流

```
合同全文（real: session.fileText / demo: getContractText(DEMO_PAGES)）
   ↓ buildIndexMap：去掉空白，记录每个字符在原文的下标
   ↓ locateQuote：先精确找，找不到再忽略空白找 → 映射回原文区间
   ↓ composeRevision / planComments：切段，处理重叠，逐条记 reason
   ↓ segmentsToParas / 批注渲染：docx Paragraph + TextRun
   ↓ Packer.toBlob → downloadBlob（复用 utils/docxExport.js）
```

## 界面上的四个出口

| 菜单项 | 行为 | 失败/边界 |
|---|---|---|
| 导出审查报告 | 打印预览 → 另存 PDF | 弹窗被拦会提示 |
| 导出合同原文（修订版） | 已采纳的修改标红替换 | 一条都没采纳时**不导出**，提示先去「修改」页采纳——避免导出「看起来改了其实没改」的文件 |
| 导出合同原文（批注版） | 全部风险挂批注，已采纳的在批注首行标「（已采纳，见修订版）」 | 定位不到的条目列在文末 |
| 只复制文字 | 3 条建议 + 3 段话术 | 剪贴板不可用时提示手动选中 |

## 已知未做

- 不支持「一键接受全部修订后重排」；修订版是终稿形态，不是可协商的工作稿。
- 批注作者统一写「签前有数」，没有多人协作/回复串。
- 表格类条款（费用明细表）没有专门排版，按普通段落输出。
