## 一、两个问题其实是同一个根因

你问的两件事——「怎么评估功能好不好」和「输出不稳定、分档标准不清」——都指向同一个缺口：**没有把现成的标准答案变成可重复执行的评测**。

- 有评测集，才能算「召回率 / 误报率 / 分档一致性」，才能跟通用大模型做同题对照——这是问题一。
- 有评测集，才能把「每次都一样」变成可验收的指标，改完 prompt 立刻知道有没有变稳——这是问题二。

10 月 10 日的 `修复与验证记录.md` 里其实已经写下这两句话：
> 「未证明优于豆包或通用大模型，未达到高质量审查的独立盲测标准」
> 「没有通过重复抽样获得稳定性或准确率估计」

当时发现了，但一直没做。这次补上。

## 二、评测怎么搭（已落地的三件套）

| 组件 | 文件 | 作用 |
|---|---|---|
| 机器可读标准答案 | `app/scripts/verify/golden-set-01.json` | A1–A14 每个维度配 3–4 个锚点词，命中≥2 个算该维度被覆盖；A3/A5/A7/A11/A14 标为必命中 |
| 重复抽样脚本 | `app/scripts/verify/eval-quality.mjs` | 同一份合同跑 N 次（默认 5），统计条数极差、召回、分档一致性、证据可回查率 |
| 通用模型基线 | 同脚本内 `BASELINE_SYSTEM/USER` | 同模型、同合同，裸 prompt 无标准卡 / 无 RAG / 无两阶段约束，作为对照组 |

命令：
```bash
cd app
node scripts/verify/eval-quality.mjs 5          # 当前线上 prompt
EVAL_PROMPT_VARIANT=fixed node scripts/verify/eval-quality.mjs 5   # 实验变体
```

判分口径写在 golden set 的 `note` 字段里，避免以后自己都忘了数字怎么来的。

## 三、实测数字（三轮对照）

| 指标 | 当前 prompt（第1轮） | 当前 prompt（第2轮） | 改措辞变体（第3轮） | 锁温度=0（第4轮） | 通用模型基线 |
|---|---:|---:|---:|---:|---:|
| 输出条数 | 5/5/5/5/5 | 5/5/6/5/4 | 6/5/5/6/6 | 5/5/5/5/5 | 12–16 |
| A1–A14 召回 | 37.1% | 41.4% | 45.7% | 37.1% | 78.6%–85.7% |
| 证据可逐字回查 | 未统计 | 100% | 100% | 100% | 77%–94% |
| 命中项分档一致性 | 90.0%* | 93.3% | 90.0% | 90.0% | — |
| 必命中项全稳 | 2/5 | 2/5 | 2/5 | 2/5 | — |

\* 第 1 轮原始汇总写 38.6%，那是把「5 次都没命中的维度」当成不一致算进去了。重算只统计命中过的维度 = 90.0%。

**三条能直接讲出口的结论：**

1. **产品链路召回只有 37%–46%，同模型裸 prompt 有 79%–86%。** 差了约一倍。「加了标准卡和 RAG 反而更差」——当前工程是负收益，这是最需要正视的事实。
2. **但不是全面更差：产品链路证据 100% 可逐字回查，裸模型只有 77%–83%。** 可靠换来了覆盖。完整的产品判断应该是「现在这条路走的是高精度低召回，而用户第一次用更需要高召回」。
3. **分档一致性其实有 90%，不稳定主要不是「同一条反复横跳」，而是「维度集合和档位分布整体漂移」**：第 2 轮 A7 从 must 变 check、A10 在 check/must 间摇摆；必命中 5 项里 3 项（押金结算、逾期抵扣、账单效力）5 次只命中 1–2 次或 0 次。用户感受到的「每次不一样」，主要是这几项时有时无 + 档位整体偏移。

**改 prompt 措辞的实验结论**：去掉「每张卡必须输出命中/未命中」（JSON 里根本没有这个字段，模型理解成每卡凑一条）+ 给 level 写判定标准，召回 41.4%→45.7%，**只涨 4 个百分点**。方向对，但不是银弹。真正的约束在 prompt 整体结构（5 张卡 + 一大堆否定式禁令），不是某一句话。

**锁温度的实验结论**：`buildChatRequest` 原来写 `Number(input.temperature) || 0.2`，传 0 会被 falsy 回退成 0.2——审查实际一直跑在 0.2。强制 0 后条数极差从 2 降到 0（5 次全是 5 条），但召回没变（37.1%），**分档照样漂（A10 只有 60% 一致）**。结论：采样随机性只解释「条数漂移」，解释不了「分档漂移」——后者必须靠规则化，不能靠调参。

## 四、问题一的答案：效果评估该怎么做

### 别再用「176/176 全过」证明功能好

`npm run test:contract-review-benchmark` 的 176/176 只证明「你不会把已支持的写法改坏」。测试样本是你自己造变体、规则照着它写的——过拟合。这个数字对外讲是减分项，对内只能当回归保护。

### 三层评估，按这个顺序建

| 层 | 指标 | 现状 | 下一步 |
|---|---|---|---|
| L1 存在性 | A1–A14 标注维度的召回率、负例误报数 | 已建，本机可跑 | 补 05 低风险负例；把 02/04 同文合同纳入，测跨格式一致性 |
| L2 正确性 | 证据是否逐字回查、解释是否把保护条件说全、分档是否符合判定标准 | 只做了证据回查（100%/77%） | 人工抽 20 条按「错判/漏保护条件/过度断言」三档打标 |
| L3 用户价值 | 用户是否因此改了条款、谈成了修改、省了钱 | 完全没有 | 埋点：采纳修改、写回正文、复查后风险消失的比例 |

**同模型裸 prompt 对照是 L1 的关键**——它回答「这套 prompt 工程到底有没有增值」。当前答案是「召回负收益、证据正收益」，必须两头都讲才诚实。

### 每次改 prompt 的验收流程（10 分钟）

```bash
node scripts/verify/eval-quality.mjs 5
```
看四个数：召回是否上升、证据回查是否仍 100%、必命中项是否 5/5、条数极差是否收窄。四个都变好才合入。这套东西本身就是 AI PM 作品集里最能讲的一段——**你不是在调 prompt，你是在建评测驱动的迭代闭环**。

## 五、问题二的答案：分档不稳定怎么治

### 先分清两种「不稳定」

| 现象 | 实测 | 根因 |
|---|---|---|
| 风险点集合漂移 | 5 次里 4 次命中相同 5 项；A5/A8/A11 各偶尔冒出来一次 | 5 张标准卡形成隐性配额；卡外维度没有稳定检查项 |
| 分档漂移 | A7 在 must/check 间变（一致 80%）；A10 在 check/must 间变（一致 60%–80%） | prompt 里 level 只写了「high 或 medium 或 low」，**没有任何判定标准**；模型每次自己重新理解 |

### 按投入排序的解法

1. **给 level 写可判定的定义（最高 ROI，改 prompt 一句话）**
   - high（必须改）：签字后直接造成金钱损失、押金没收、单方涨价、无条件换锁、个人信息外泄或丧失法定权利
   - medium（建议确认）：条件或程序明显不利，但要结合实际执行判断
   - low（仅提醒）：正常条款中值得留意之处
   - 本次实验中已验证：单独改这条，分档一致性没有显著提升（93%→90%，在噪声范围内），但它是后续所有规则的前置条件——没有定义就没法写规则。

2. **分档从模型手里收回来，改成确定性规则（真正解决漂移）**
   模型只负责「命中了什么 + 原文证据」，分档由代码算：
   ```
   high   ← 后果含押金没收/单方涨价/换锁/个人信息共享 + 证据已核验
   medium ← 条件不利但存在保护条款/需结合实际
   low    ← 合理期限、正常损耗、措辞可再完善
   ```
   落点：`riskMapper.js#levelFromSeverity` 现在只看 severity + confidence。让 AI 输出结构化的 `consequenceType` 和 `hasProtection`，规则据此定档。**这是产品决策，不是模型调参**——把「什么算必须改」写成你能讲清楚、能改的规则，正是 PM 该干的事。

3. **扩标准卡到 8–10 张，但去掉「每卡必输出」的配额语义**
   补：个人信息共享、代收费用开放清单、交付验收期、恢复原状标准。同时把卡片明确定位成检查清单，允许「检查了但没命中」——这次实验已经证明光改这句话只值 4 个点，得连同 prompt 结构和卡片数量一起改。

4. **固定采样参数 —— 本次已完成**
   - 修复 `server/ai-chat-request.mjs` 的 falsy bug：原来 `Number(0) || 0.2` 让 0 永远失效，改为显式判断 `undefined/null`。
   - `src/features/aiReview.js` 审查请求显式传 `temperature: 0`。
   - 实测效果：条数从 4/5/6 漂移收敛到 5/5/5/5/5。**分档漂移仍在，需要靠第 2 条规则化解决。**

5. **界面层兜住信任**
   分档旁边标「AI 判断，建议结合原文核对」；同一风险维度不要因为分档变化就换位置——按维度 id 排序而不是按档位排序，用户就不会觉得「每次整个页面都变了」。

## 六、局限（必须跟数字一起说）

1. **只有一份合同的两轮抽样**。A1–A14 的锚点命中是「有没有提到这个词」，不代表解释正确。要形成对外口径，至少补 02 高风险、03 Word 冲突、05 负例，各跑 5 次。
2. **基线不是「豆包 / GPT」**，是同一个 deepseek-v4-flash 裸 prompt。它回答的是「prompt 工程有没有增值」，不是「我们比其他模型好不好」。要做模型对比，得换 provider 再跑同一套脚本。
3. **证据回查率 100% 不代表法律正确**。当前 prompt 要求逐字引用，模型照做了；但它对「这条是不是真的对用户不利」的判断仍需人工抽检。
4. **满意度/采纳率无任何数据**。L3 为空，不能声称「帮用户省了钱」或「提升了效率」。
