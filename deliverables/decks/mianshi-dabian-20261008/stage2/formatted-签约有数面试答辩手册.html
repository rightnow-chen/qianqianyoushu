一、面试官两连问的标准作答

（一）这个产品是给谁用的？（用户与场景）

目标用户（详细、具体、有身份、有习惯、有设定）：小张，23 岁，应届毕业生，即将赴深圳入职一家互联网公司做运营，月薪 7K。第一次租房，预算 2500-3500 元/月，押一付三一次要拿出上万。习惯在小红书、贝壳上看房，签约前会搜「租房避坑」，但信息碎片化、真假难辨。设定：入职报到前 2 周必须落定住处——时间紧、无经验、无人可问。

反向求证（可标准化）：这一类用户需求类似——都是首租、都缺法律常识、都预算有限、都面临「当场要签」的时间压力。避开了「谁都可以用 = 谁都不会用」的定位陷阱。

典型场景（按行为动线）：看中房源 → 中介发来合同 PDF → 通读 10 分钟看不懂关键条款 → 搜避坑帖越搜越乱 → 中介催「今天定才有优惠」→ 时间压力下硬着头皮签字 → 入住后退租时被「无任何损坏」条款扣押金。

三、面试官可能的质疑与回答（Q&A 预案）

Q1：租房是低频事件，凭什么说「高频高痛」？

  诚实口径——对个人低频（1-2 年一次）但极高痛：单次不可逆、损失 1-2 个月房租、信息严重不对称；对人群高频持续：每年 900+ 万毕业生进入租房市场，毕业季集中爆发。工具型产品不靠频次留存，靠「用时必到」；且「签约」是租房动线的必经节点，无法跳过。

Q2：用户为什么不直接把合同丢给豆包 / Kimi？你的壁垒是什么？

  三点——①可核对性：通用模型会编造条款（幻觉），我们把「结论必须逐字命中原文」做成硬校验，无出处直接丢弃；②场景深度：55 类租房专属规则（押金、涨租、入户、管辖）而非泛泛的风险提示；③闭环：不止给结论，还给话术、生成修订合同——通用模型给完清单就结束了。通用 AI 是能力，我们把能力做成了可靠的产品流程。

Q3：AI 结论错了怎么办？出了问题谁负责？

  三层防线——①本地规则库先出结论（确定性），AI 只做补充解释与话术；②证据逐字校验，无出处不出结论；③法条溯源可人工核对，产品边界明示「提供协商依据，不构成法律意见」。已建立 29 类风险场景基准测试做回归（当前漏检 0 / 误报 0）。

Q4：律师审查更专业，用户为什么不找律师？

  不对标专业深度，对标「用得起、等得起」：律师 200-500 元/次、1-2 天交付；我们 <0.1 元/次、30 秒。定位是「签约前功课」而非法律意见，律师是升级路径而非竞品。

Q5：你怎么验证这是真需求？做过用户测试吗？

  已设计小样本验证（3-5 位目标用户走完主流程，观察能否复述风险原因、找到话术、说出下一步动作）；演示案例覆盖预算超支、合同风险、信息缺失三类结局。诚实说明：当前为作品集阶段，验证是小样本加计划，不夸大成已有数据。

Q6：商业模式与 ROI 怎么算？

  单次审查 Token 成本约 0.05-0.1 元；潜在付费点为单次审查 9.9-29.9 元、与租房平台或毕业季社群合作分成。当前阶段核心价值是求职作品集，商业化是后续路径，ROI > 1 有清晰路径。

Q7：你砍掉了很多功能，依据是什么？

  四条判据——主线判据（不服务「看懂 + 谈清楚」的不做）、连坐判据（上游表单砍则下游费用测算连带砍）、门槛判据（反对「先填一堆再给价值」）、砍而不弃（进 P1 排队）。结果：P0 从 15 项缩到 12 项，主线闭环「审合同 → 谈判台 → 复查」。

Q8：技术含量在哪？不就是 prompt 工程吗？

  系统工程四层——规则引擎（55 类风险 × 触发条件）、证据校验（逐字匹配 + 丢弃机制）、降级兜底（模型不可用时本地照常出结果）、评测闭环（29 类场景基准回归 + RAG 评测集）。AI 只是其中一层，产品的可靠性来自另外三层。

Q9：这个领域有竞品吗？空白市场是不是伪需求？

  有对标——直接竞品是通用合同审查 SaaS（需求已被 B 端验证），间接竞品是通用大模型，非互联网竞品是律师。我们不做空白市场，做的是「把已验证的需求平移到被忽略的 C 端租客场景」。

Q10：合同是敏感数据，隐私怎么处理？

  默认「仅本地分析」模式，合同不出设备；开启远端时仅发送本次任务所需内容，服务端日志不落合同全文；API 密钥只在服务端环境变量；提供一键清除全部本地数据。

四、普通产品 vs AI 产品（为什么这个需求适合用 AI，不能用固定规则？）

回答思路：把产品的 workflow 逐步拆开，逐环节回答「普通规则只能……，而需要 AI 的……能力」。结论先行：签约有数不是「万物上 AI」，而是「规则保下限、AI 抬上限」的混合架构——能用规则坚决用规则（确定性、可回归测试），AI 只用在规则不可替代的三个环节。

Workflow 环节普通规则能做到是否需要 AI需要的 AI 能力
① 合同导入与条款切分文本切分、条款定位、OCR 文本清理——确定性任务不需要—
② 风险初筛（55 类规则匹配）触发条件明确的场景（押金、违约金、管辖）规则是主力：确定性输出、可回归测试（29 类场景漏检 0 / 误报 0）不需要，刻意用规则—
③ 措辞变体识别与长尾兜底只能命中已枚举的关键词；房东把「押金」写成「保证金」、「无损坏退还」改成「验收合格后返还」就会漏需要语义理解：措辞等价归类 + 规则库外可疑条款发现
④ 场景化后果解释只能输出静态提示文案「注意押金条款」需要（核心价值）结合本合同原文与用户场景推理后果：「这句话意味着退租时房东能以地板划痕为由扣全部押金」
⑤ 谈判话术生成只能给与合同无关的万能模板需要（核心价值）上下文生成：基于条款风险 + 合同原文 + 谈判进展，生成可直接发送的话术
⑥ 修订写回与二次复查写回是确定性替换；复查复用 ①②③写回不需要；复查需要③兜底同③
⑦ 法条溯源法条来自本地法条库检索引用AI 仅做组织，不允许生成法条检索结果的组织引用（防幻觉设计）

标准作答（一句话版）：普通规则只能命中已知措辞、给出静态提示，而我产品 workflow 中的措辞变体识别、场景化后果解释、谈判话术生成三个关键功能，需要用到 AI 的语义理解与上下文生成能力——这是我产品的核心价值；同时风险初筛、证据校验、修订写回我刻意保留规则实现，因为法律场景要确定性：规则保证下限（可回归测试），AI 抬高上限（泛化与生成）。

Q11：你已经有 55 类规则库了，把 AI 拿掉，产品还剩什么？

  剩一个「条款定位器」：能标出可疑条款，但解释不了后果、生成不了话术、覆盖不了措辞变体和长尾。AI 在产品里贡献三件事——语义泛化（变体识别）、后果推理（场景化解释）、话术生成（上下文相关），这三件恰恰是用户价值最高的部分。反过来只留 AI、去掉规则也不成立：结论不可复现、无法回归测试、还有幻觉风险。所以我的答案是混合架构：规则定下限，AI 拔上限，两边的贡献都能说清楚。

Q12：维护同义词表 / 关键词库也能扩大匹配面，为什么非要上大模型？

  因为措辞是开放集合，不是有限集合：房东会刻意避开常见词（写「保证金」不写「押金」）来规避模板化审查，同义词表永远在追长尾，维护成本线性涨、覆盖率不收敛。语义模型的边际成本固定，还能发现「规则库根本没收录」的可疑条款。另外我做了双通道：规则先召回、AI 兜底补漏，规则漏掉的不是静默丢失，而是被 AI 标出来。

Q13：AI 生成的解释和话术错了怎么办？它会编造法条吧？

  三道约束——①AI 不自由裁量风险：风险结论由规则库先判定，AI 只做解释与话术的「翻译」，不允许推翻或新增结论；②法条只准引用本地法条库的检索结果，提示词明确禁止生成法条号，杜绝编造；③输出硬校验：解释和话术里引用的合同原文必须逐字命中原文，命中失败整条丢弃。也就是说，AI 的自由度被限制在「换一种人话讲」和「组织话术」，事实层全部由确定性组件把守。

五、产品定位：工具、助手还是 Agent？

判断标准：工具＝用户驱动每一步、输入输出固定；助手＝对话式交互、给建议但由人执行；Agent＝自主「感知-规划-执行-反思」，能自己拆解目标并调用工具完成多步任务。

标准作答：签约有数目前是一个「规则为骨架、AI 为增强」的垂直场景智能助手，带一条局部自动化链——主流程「审合同 → 谈判台 → 复查导出」由用户驱动、结构固定，是工具特征；谈判军师多轮对话、按房东回应动态调整话术，是助手特征；「修订写回 → 自动重新审查 → 验证风险是否真的被改掉」是给定目标后自主执行的多步链，已经有局部 Agent 特征。它还不是成熟 Agent，差距主要有四点——

  • 自主规划：流程是产品预设的，不会自己拆解新目标（用户不投合同它不自己找活干）；
  • 开放行动空间：只能「生成」，不能「执行」——不会替用户把话术发给房东、不会直接改合同；
  • 跨会话记忆：状态只在单次审查流程内，不积累用户偏好与谈判历史；
  • 运行时自我反思：正确性靠离线回归测试保证，而不是运行中自我纠错。
关键态度：前两条（尤其「不替用户执行」）是我在法律场景下的刻意产品选择——谈判立场和底线只有用户自己知道，全自动意味着错误无人把关、用户失去掌控。我的设计原则是「AI 生成、用户决策」（human-in-the-loop），每一步可核对、可否决。所以「还不是 Agent」里有一部分是边界选择，不是技术欠账。

Q14：这不就是个「上传 → 点按钮 → 出报告」的工具吗？凭什么说是助手？

  看交互重心：工具是「人找功能」，助手是「理解意图后主动供给」。军师环节是真正的多轮对话——它会追问合同里没写清的信息、根据房东的回应调整下一轮话术，而不是一次性输出；复查链也是给定目标后自动串联多步执行。纯工具做不到这两点。但我也不硬吹：主流程骨架确实是确定性的，这是法律场景要可核对性的必然选择。

Q15：为什么不做成全自动 Agent？用户丢一份合同进去全部谈好改好，体验不是更好吗？

  两个理由——①容错：合同审查错一条的代价是真实金钱损失，全自动等于错误无人把关，我的架构宁可让 AI 只做有出处的生成；②谈判本质是用户本人的事：预算底线、是否长租、和房东的关系，这些只有用户知道，Agent 替用户谈判在法理和情理上都立不住。所以我把 Agent 能力收敛在「准备弹药」环节（审查、话术、修订草案），「扣扳机」永远留给用户。这不是做不到，是不该做。

Q16：和成熟的 Agent 产品相比，缺的特征打算什么时候补？

  路线图上优先补「运行时反思」——复查环节已有雏形（审查→对比→结论的自动闭环），下一步是把离线回归测试搬到运行时做自检；然后是「跨会话记忆」——记住用户的房源与谈判历史，二次续谈不用重讲背景。自主规划和开放行动空间会谨慎放开：先做「建议执行」（用户一键确认后由产品代发话术草稿），而不是直接自主行动。

Q17：下一代通用大模型直接内置「合同审查」，你这个产品的定位不就没了吗？

  通用模型迭代的是能力，我的产品沉淀的是流程与数据：55 类租客视角规则、本地法条库、谈判三态跟踪、修订写回与复查闭环——模型再强，也需要有人在具体场景里把它组织成「可核对、可追责」的流程。而且我的架构是模型无关的（Provider 可切换），新模型更强对我意味着成本下降而不是被替代。通用大模型是发动机，我的产品是装了方向盘和安全带、按租客场景调校过的那辆车。

六、MVP 功能优先级：为什么先做这些功能？（用需求分析三步法推导）

回答原则：核心价值 + 风险兜底。不是拍脑袋列功能清单，而是走完「真伪筛选 → 范围收敛 → 优先级排序」三步，每一步都有判据、可复述。

Step 1 需求真伪筛选（为什么值得做）

  • 5Why 追问：用户说「帮我审合同」→ 为什么要审？怕被坑 → 为什么怕？第一次租房不懂条款 → 为什么不搜攻略？信息碎片、真假难辨、越搜越乱 → 真实动机不是一份审查报告，而是「签约前确认自己不会吃哑巴亏」——所以产品终点不是「告诉你有坑」，而是「帮你把坑谈掉、改掉」。
  • 用户分层：核心用户 = 第一次租房的应届生（签约是必经节点、有时间压力、零经验、损失不可逆）；边缘用户 = 换租白领、房东侧。边缘需求（历史租金比价、房源聚合）不进 1.0。
  • 成本-收益验证：单次审查 Token 成本 0.05-0.1 元 vs 律师 200-500 元/次；技术全部成熟（规则引擎 + LLM 理解，无需训练模型）——收益远大于成本，真需求。
  • MVP 快速验证：全流程已实际跑通 + 29 类风险场景回归测试（漏检 0 / 误报 0）；计划 3-5 位目标用户小样本走查（观察能否复述风险原因、找到话术、说出下一步动作）。

Step 2 需求范围收敛（做多大）

  • 最小 MVP：只做「审合同 → 谈判台 → 复查导出」三步闭环，拒做大而全。
  • 独立模块拆分：合同审查（导入→切分→规则初筛→AI 兜底→证据绑定）、谈判台（话术→回应记录→三态跟踪）、修订复查（写回→重审→导出）各自独立实现，模块间以数据契约衔接，任何一块可单独迭代。
  • 迭代 Roadmap：V1.0 = 现有三步闭环；V1.1 = 房源与预算表单作为独立版本回归、军师质量评测扩展；V2.0 = 建议执行（用户一键确认后代发话术）、跨会话记忆。

需求的完整闭环不是只排优先级，每个迭代都覆盖三类需求：

需求维度签约有数的对应设计
主流程需求（核心）导入合同 → 逐条风险 + 大白话解释 + 原文证据 + 法条 → 生成谈判话术 → 谈妥条款写回 → 修订版合同导出
边缘流程需求（辅助）OCR 扫描件导入；法条点开核对原文；修订版导出为 DOCX
异常流程需求（兜底）模型不可用 → 本地规则库照常出结果；AI 引用证据未逐字命中原文 → 整条丢弃不出结论；隐私敏感 → 仅本地模式，合同不出设备

异常兜底三件套（降级、防错、止损）是风控思维的产品化：法律场景下「宁可少说，不能说错」。

Step 3 优先级排序（P0-P5，三维度评估）

P0 功能影响面价值（痛点严重度 / 可替代性）频次（动线必经度）
合同审查 + 证据绑定100% 用户必经不可逆金钱损失；通用 AI 有幻觉、不可核对 → 必须自建每单必到
谈判台有风险条款即需谈判，约 100%风险清单不落地就是纸面安慰；竞品都停在「给清单」审查后必到（除非合同零风险）
修订合同 + 复查谈妥后必经口头承诺最容易丢；人眼看不出「改了 A 条改坏 B 条」谈判后必到，闭环终点

排序结果：P0 = 审查+证据绑定、谈判台、修订复查（合计 12 项功能点）；P1 = 表单回归、OCR 增强；P2-P3 = 多模型切换、语音输入；P4-P5 = 费用测算、签约判断、社区比价。1.0 只聚焦 P0。

先不做的功能及原因（成本 / 前置依赖 / 发展阶段）

砍掉的功能判据去向
房源与预算表单 + 费用测算前置任务依赖（表单是测算的上游，砍表单则测算连坐）+ 门槛判据（反对「先填一堆再给价值」）P1，作为独立版本回归
签约判断（三级决策）发展阶段考量：1.0 定位「签约前功课」不做决策代理，责任边界重本版砍掉，随主线收敛
房源聚合与比价成本考量：需外部数据源与实时性维护，且不服务「看懂 + 谈清楚」主线不做清单
社区 / 攻略内容成本考量：重内容运营，偏离工具定位不做清单
收尾一句话：签约有数为第一次租房的应届生解决「合同看不懂、有坑不会谈」的痛点，P0 只做「审合同 → 谈判台 → 复查导出」核心闭环，不做低主线价值的费用测算与比价功能，靠证据绑定 + 法条溯源打磨差异化。

Q18：砍掉的功能以后又需要了怎么办？会不会砍错？

  三条保险——①砍而不弃：全部进 P1 排队并写明回归条件，不是删除；②判据可复述：每一条砍掉的功能都能指出违反了哪条判据（主线 / 连坐 / 门槛），不是拍脑袋；③上线验证：1.0 上线后跟踪功能请求率与用户访谈，若「费用测算」被高频提及就提前排期。砍错的方向成本远小于同时做错十个方向。

Q19：谈判台用一两次就没用了，这种低频功能凭什么进 P0？

  工具型产品的频次要换算成「动线必经度」：审查完不去谈，风险永远是纸面风险，产品就停在「告诉你有坑」——价值直接减半。签约是租房动线无法跳过的节点，谈判是签约动线无法跳过的环节，宁可做窄做透。另外低频不等于低价值：单次涉及金额上万，一次成功谈判的回报覆盖整个产品成本。

Q20：P0 有 12 项功能，这也叫 MVP？

  12 项是「三步闭环的最小完备集」：拆掉证据绑定，可信性塌；拆掉三态跟踪，谈判就没法管理；拆掉二次复查，闭环断在最后一米——任何一项缺失流程就不完整。而且我做过对照：通用合同审查 SaaS 的功能清单是这个量级的数倍。判断 MVP 的标准不是功能数量，而是「拆一项就断链」。

Q21：二次复查是不是伪需求？用户自己看一眼改完的合同不就行了？

  人眼看不出「改了 A 条把 B 条改坏了」：修订是字符串级替换，可能引入新的格式条款或丢掉原有保护性约定。二次复查做的是机器级 diff——重跑 55 类规则，对比修订前后风险清单，确认风险真的消除而不是转移。这正是「把用户的确认动作标准化」：靠感觉变成靠回归。

七、产品核心流程设计：为什么是「审合同 → 谈判台 → 复查导出」？

总回答：我把应届生签约前的一系列显性业务动线和思考过程——「这份合同有没有坑？我该怎么跟房东谈？谈完改完真的没问题了吗？」——拆成一个标准化、可执行、可兜底的三步流程。每一步对应一个用户心智问题，每一步的输出就是下一步的输入，每一步都有降级兜底。

步骤心智问题解决什么关键设计兜底
① 审合同「有没有坑？」看不懂：术语门槛 + 不知道后果55 类规则初筛 + AI 变体兜底；逐条绑定原文证据 + 法条溯源；大白话后果解释模型不可用 → 本地规则照常出结果；证据不命中 → 不出结论
② 谈判台「怎么谈？」不会谈：没话术、没筹码、谈完没记录军师按条款生成可直发话术；房东回应记录；条款三态跟踪（待谈/谈中/已谈妥）军师离线 → 规则库预案话术；仅本地模式明示降级
③ 复查导出「真的没问题了吗？」口头承诺没落纸面；改 A 坏 B谈妥条款一键写回 → 自动重审 → 风险清单 diff → 修订版 DOCX 导出导出失败本地保存；校验失败条款标记不写回

为什么是这个顺序：①与用户行为动线同构——先看懂才敢谈，谈完要确认，顺序不能颠倒；②数据流与心智流一致——审查的风险结论是话术生成的输入，谈妥的条款是修订写回的输入，环环相扣不断链；③三步相互独立、可自由跳转，但默认线性引导——降低首次使用的决策成本。

一句话版：我的核心流程是把「有没有坑 → 怎么谈 → 改好了吗」这条隐性思考链，拆成审合同、谈判台、复查导出三步——标准化（每步有固定产出）、可执行（每步有明确动作）、可兜底（每步有降级预案）。

Q22：为什么是三步？两步或四步不行吗？

  三步对应用户心智的三个必答问题（有没有坑 / 怎么谈 / 改好了吗）：少一步就断链——砍掉谈判台，风险清单落不了地；砍掉复查，修订结果无人验证。多一步就是打扰——比如独立的「风险评估报告确认页」，信息在审查页已经有了，单独成步只会拖长动线。三步是「拆一项就断、加一项就赘」的平衡点。

Q23：流程是不是太线性？用户想直接改合同、跳过谈判台怎么办？

  支持跳步：三个模块在导航上平等可达，任何一步的产出都可以单独使用。但默认动线是线性引导——首次用户按推荐路径走，减少「下一步点什么」的决策成本；熟练用户自由跳转。线性是默认值而非强制锁，这是引导性和灵活性的平衡。

Q24：为什么不让流程自动串联——上传合同直接出修订版，一键到底？

  两个原因——①每一步都是用户消化信息的必要节奏：跳过「看懂」直接拿修订版签字，等于把判断权又交了出去，反而放大风险；②谈判的中间态只有用户知道（房东说了什么、让到了哪一步），机器无法代填。自动化我用在该处：复查链（写回→重审→diff）内部全自动，因为那是纯机器可验证的环节。

Q25：这条流程哪一步最容易流失用户？怎么兜？

  诚实说：审查 → 谈判台之间。用户看完风险清单，最常见反应是焦虑而非行动——问题从「不知道有坑」变成「知道了但不敢谈」。对策：风险条目旁直接给「下一步怎么办」——话术入口、替代条款、法律依据一键展开，把焦虑时刻转化成行动时刻。流失监控也埋在这条边：从审查完成到首次使用谈判台的转化率，是 1.0 最核心的漏斗指标。

八、怎么定义产品的「好」？核心功能是怎么设计的？

面试官的问题：怎么定义产品的「好」？你的核心功能是怎么设计的？——两个问题是递进的：定义「好」是先立尺子，核心功能设计故事是拿尺子量出来的过程。切忌把「好」回答成「体验流畅、界面美观」这类不可验收的形容词。我的核心功能不止一个（审查、证据绑定、法条溯源、谈判台、修订复查五个），下面先立尺子，再逐一讲每个功能的设计思路。

先立尺子：产品「好」的三问递进

递进问题签约有数的回答可验证口径
有用吗（解决真问题）需求真伪三步法验证过：真实痛点（不可逆金钱损失、时间压力）、成本收益成立（单次 <0.1 元 vs 律师 200-500 元）、MVP 已实际跑通风险识别准确率：29 类基准回归漏检 0 / 误报 0；签约前完成审查的用户占比
好用吗（价值能兑现）用户能否走完「看懂 → 谈掉 → 改好」闭环，而不是拿到风险清单就关掉审查 → 谈判台转化率（北极星漏斗）；话术采纳率；10 分钟内走完全流程
值得投吗（有前景）每年 900+ 万毕业生持续流入；单次成本 <0.1 元；55 类规则 + 法条库 + 流程沉淀构成壁垒；架构模型无关，模型进步 = 成本下降单位审查成本走势；功能请求率（决定 P1 排期）
一句话定义：签约有数「好」= 用户签约行为被改变——从「硬着头皮签字」变成「带着结论、话术和修订版合同去和房东谈」。落成可验收标准：走完流程的用户能复述至少 3 条风险的原因、找到对应话术、说出下一步动作。（详细指标分层见配套《签约有数-指标体系与测试设计》。）

核心功能设计故事（逐一，用 badcase → 迭代 → 沉淀）

我的核心功能有五个：①合同审查（规则+AI 双通道）②证据绑定 ③法条溯源 ④谈判台 ⑤修订复查。每个都经历过「先做一版 → 发现 badcase → 迭代 → 沉淀原则」的过程，下面逐一讲。

功能一：合同审查——为什么用「规则优先、AI 兜底」双通道

第一版设计：直接让 AI 看合同、输出风险——最快，demo 当天就能跑。

发现的 badcase：AI 对同一份合同两次审查结论不一致，且会漏掉已明确写死的风险（如「押金在无任何损坏时退还」这种套话），因为它靠「理解」而非「匹配」。法律场景下「结果不可复现、会漏」是不可接受的。

迭代后的设计：拆成双通道——①规则通道先行：55 类租客视角风险规则（押金/涨租/维修/解除/入户/管辖/格式条款），每条带触发关键词、风险解释、修改建议、以及「原文/替换文」对照；②AI 通道兜底：只处理规则没覆盖的措辞变体与长尾。模型不可用时规则照常出结果，审查不中断。

沉淀思考：AI 产品里，把「确定该对的」和「需要泛化的」分层处理，比「全交给模型」更可靠——确定性环节用规则（可回归、可复现），只有泛化环节才用模型。

功能二：证据绑定——无证据不出结论

第一版设计：AI 直接输出风险结论和解释，不附原文出处。

发现的 badcase：用户第一反应不是「好准」，而是「这条合同里真的有这句话吗？」——AI 会改写、概括甚至编造条款（幻觉），结论无法核对；误报会让用户拿着不存在的问题去和房东谈，一次翻车摧毁全部信任。这违背法律场景最底层习惯：白纸黑字才可信。

迭代后的设计：①每条结论必须逐字命中合同原文，命中失败整条丢弃；②规则库先出结论，AI 只做解释与话术的「翻译」，事实层全部由确定性组件把守；③29 类风险场景基准回归守门（漏检 0 / 误报 0）。

沉淀思考：①AI 产品里信任比智能稀缺——可核对性是信任成本最低的来源；②正确姿势是用确定性组件守住事实层，把模型自由度限制在表达层。

功能三：法条溯源——结论要有依据，依据要可查

第一版设计：让 AI 在解释风险时顺便「引用相关法条」。

发现的 badcase：AI 会编造法条号或张冠李戴——说「根据《民法典》第 X 条」，但那条根本不是讲押金的。用户拿去和房东对质，一旦被识破，信任崩塌比没有法条更糟。

迭代后的设计：①本地法条库：把租房高频法条（《民法典》租赁合同章节等）预先整理进 `legalBasisMap`，按风险类型映射；②只准引用、禁止生成：提示词明确禁止模型自己写法条号，法条内容一律从本地库检索并点开可核对原文；③法条作为风险条目的附注，而非模型的自由发挥。

沉淀思考：生成式模型可以「组织」知识，但不能「发明」知识——凡是能被验证的东西（法条、数据、事实），都该指向一个可信来源，而不是让模型现编。

功能四：谈判台——从「给清单」到「帮你谈」

第一版设计：审查结束后给一份风险清单，配上万能话术模板，到此为止。

发现的 badcase：用户看完清单最常见的反应是「知道了，但我还是不敢谈」——清单把「不知道有坑」变成了「知道有坑但无力应对」，焦虑反而更重；万能话术模板脱离具体条款，发出去很生硬，价值停在纸面。

迭代后的设计：①军师多轮对话：按当前条款 + 合同原文 + 谈判进展，生成可直接复制的话术，并追问合同里没写清的信息；②条款三态跟踪：每条风险按「待谈 / 谈中 / 已谈妥」管理，记录房东回应与让步结果，让谈判不再靠脑子记；③谈妥即写回：已谈妥内容一键写入修订合同，形成闭环。

沉淀思考：工具的价值不在「告诉用户问题」，而在把问题推进到可行动——清单是终点，谈判台是动作的起点。三态跟踪的本质，是把一段失控的口头拉锯变成一个可管理的过程。

功能五：修订复查——改完要能证明真的改好了

第一版设计：谈妥后由 AI 直接生成一份「修订版合同」给用户。

发现的 badcase：①AI 生成会改动未谈妥的条款，用户分不清哪句是自己同意的、哪句是模型自作主张；②「改了 A 条把 B 条改坏了」人眼看不出——字符串级替换可能引入新格式条款或丢掉原有保护约定；③口头谈妥没落进白纸黑字，等于白谈。

迭代后的设计：①只写回谈妥项：仅把用户标记「已谈妥」且确认过的条款写入，AI 不擅自改别的；②修改前后对比：修订面板明确展示「原文 → 修改后」，每一步都可追溯；③写回后重新审查：重跑 55 类规则，对比修订前后风险清单，确认风险真的消除而不是转移，再导出修订版 DOCX。

沉淀思考：「生成」之后的「验证」才是闭环的最后一米——把用户「靠感觉确认改好了」升级成「靠回归确认改好了」，这是把确认动作标准化的关键一步。

五条设计思路的共同主线：法律场景下，我始终遵循「规则保下限、AI 抬上限；生成交给模型、事实交给确定性组件；宁可少说，不能说错」。这五条不是孤立的功能，是一条贯穿始终的产品原则在不同环节的落地。

Q26：「好」的标准是你自己定的，3-5 人小样本能说明什么？

  诚实口径：作品集阶段，小样本验证的是「方向对不对」（用户能否复述风险、找到话术、说出下一步），不是「数据好不好看」。关键是先把尺子立出来——漏斗指标和行为验收标准在上线前定义好，避免「先跑量再找理由」。这套口径任何一个后续拿到真实流量的版本都能直接复用，这是现在做定义的价值。

Q27：证据逐字绑定会不会太严？AI 概括改写更可读，全丢弃不误杀吗？

  法律场景两类错误的代价不对称：误信一条编造的结论，用户可能去谈一个不存在的问题、甚至签得更放心——代价是真实金钱；误杀一条概括，损失的是一点可读性。所以宁可误杀、不可误信。覆盖下限由规则库保证（规则命中的场景不经过 AI 丢弃逻辑）；被丢弃的条目在演进路线里会降级为「低置信提示」而非静默消失。

Q28：AI 全挂了只剩本地规则，产品还「好」吗？

  还成立——这正是我把「好」定义在架构层而不是模型层的证明：结论、证据、法条、复查全部来自确定性组件，模型只增强解释与话术的表达。AI 离线时产品退化为「规则版审查器」，下限仍在、只是上限降低。「好」不依赖某个模型在线，这是法律场景该有的冗余设计，也回应了「定义好不好」要可验证：下限可回归测试，上限可小样本观察。

Q29：你的北极星指标是什么？为什么不是审查合同数？

  北极星：审查完成后 7 天内使用谈判台、且至少采纳 1 条话术的用户占比——「带着武器去谈判」的比例。它同时校验「有用」（风险被识别）和「好用」（价值兑现成行动）。不选审查合同数：那是虚荣指标，用户审完就关恰恰说明价值没落地；也不选日活：工具型低频产品看日活会把自己带偏。

Q30：法条溯源这种「锦上添花」的功能，为什么不先砍掉？

  它不是装饰，是信任的组成部分：证据绑定回答「结论对应合同哪句话」，法条溯源回答「凭什么说这句是坑」。缺了后者，用户对「为什么这是风险」只能靠信 AI，而 AI 恰恰是最不可信的那一环。而且它成本极低——本地法条库是静态数据，一次整理长期复用，性价比远高于其他功能。法律场景下「可核对」不是加分项，是及格线。

Q31：五个核心功能，哪个是你最得意、最能体现产品能力的？

  证据绑定。因为它不是一个「加个字段」的 feature，而是一个架构决策：它决定了「规则先出结论、AI 只做翻译、无出处不出结论」整套事实层/表达层的分层设计，谈判台的话术、修订的写回、法条的引用全部建立在它的信任底座上。别的功能可以被替换，证据绑定是我这个产品「好」的支点——它把 AI 从「不可信的答案机器」变成了「可核对的审查工具」。

九、指标体系与测试设计：怎么判断产品可用、可信？

面试官的问题：你是怎么设计测试集合指标体系的？你怎么判断你的产品可用或可信？——承接第(7)问「定义好」继续深入：第(7)问立的是产品级的尺子，这一问答的是工程级的尺子。

总：三维度指标体系

维度回答的问题判断标准
基础验证（可用）工作流能不能完整执行？全流程走通、AI 链路健康、失败必有兜底

可用与可信的判断口径：可用 = 基础验证全绿（流程能走完、AI 挂了不空窗）；可信 = 功能验证 + 产品验证达标（漏检误报是硬断言、每条结论可溯源、降级透明）。

测试集怎么设计（按测试目的专门设计，尽量模拟真实场景）

  • 每类风险 ≥3 种独立表述变体（29 类场景）——测的是「理解」不是「匹配」，防止单一措辞过敏。
  • 黄金集 + 对照组：既有埋满标准风险的失败合同，也有零风险干净合同——双通道断言漏检与误报。
  • 合成生成器 + seed：同 seed 逐字节可复现（便于复现漏检）、异 seed 必须不同（防生成器退化为模板）、合同标注 fictional 且自带标准答案。
  • 脱敏真实失败合同进基准——尽量模拟真实用户场景，不用凭空编的理想样本。
  • 每条用例带唯一 id + 期望答案，任一失败退出码 1——评测不是打印好看的报表，是门禁。
面试金句：「可信的核心指标是证据可溯源率——AI 报的每条风险必须逐字引用合同原文、带行号定位，用户能自己核对，这条是 100% 断言，做不到就不许上线。可用性的底线是永不空窗——AI 挂了走本地规则预案，且明确告诉用户现在是本地模式还是服务离线，降级也要透明。」

Q32：基准集是你自己出的，自测自评怎么保证不是循环论证？

  三重防自证——①变体独立：合成生成器异 seed 必须产出不同合同，防生成器退化成模板套圈；②对照组设计：零风险合同必须零报告，堵住「宁可多报不担责」的捷径；③外部样本：脱敏的真实失败合同进基准，答案来自公开纠纷场景与法条定义，不是从实现反推。诚实说明：29 类覆盖的是高频长尾有限，真实合同分布会随 badcase 回流滚动扩充。

Q33：指标都通过了为什么还说有缺口？产品到底可不可信？

  缺口要分级说：已达标的是「结论可靠性」层（漏检/误报/溯源/检索，全部硬断言）；缺口在「体验层」统计（采纳率、延迟 p95）和降级 e2e 自动化。可信的判断不依赖没测的指标——因为架构上结论层与体验层解耦，结论层的可信有 100% 断言守门。缺口每一条都清楚在哪、为什么缺、排期是什么——「清楚自己缺什么」本身就是可信的一部分。

Q34：29 类 × 3 变体也就九十来条用例，够吗？

  分层回答：对规则通道够——规则逻辑有限可枚举，全量场景可以覆盖；对 AI 兜底层确实不够——所以 AI 层另设评测（RAG 56 条 + 军师真模型采样），并用架构约束兜住风险：AI 结论必须过证据逐字校验，不命中即丢弃，影响面天然有限。用「影响面可控」换「验证成本可控」，上线后真实 badcase 回流进基准滚动扩充。

Q35：采纳率还没统计，那你的北极星指标怎么算？

  口径已定义（审查后 7 天内使用谈判台且采纳 ≥1 条话术），数据结构 negotiationStates 已就位，缺的只是汇总统计这一步工程实现——属于「会做没做」，不是「不知道怎么算」。作品集阶段先立口径、后补管道，这个顺序是刻意的：先保证测的东西是对的东西。

十、一句话介绍：如果让你用一句话定义这个产品，它到底是什么？

回答思路：一句话要收口到「品类 + 人群 + 差异点」，且与产品定位自洽（垂直场景智能助手，不是通用聊天、不是全自动 Agent）。不同受众用不同版本，但内核一致。

版本一句话适用场合
标准版（默认）签约有数是一个帮第一次租房的应届生在签约前看懂租房合同的 AI 审查工具——粘贴合同 30 秒出逐条风险，每条附原文证据和法条依据，还能生成谈判话术、谈妥后出修订版合同。面试自我介绍、产品定义题
用户利益版签约前 10 分钟、不到 1 毛钱，帮你把合同里的坑找出来、谈掉、确认改好。对用户/对非产品背景的人
类比版租房合同的「体检中心 + 谈判军师」——把律师 200 块一次的签约前审查，做成 1 毛钱的 AI 功课。要记忆点、快速传播的场合
定义收口：它到底是什么——一个垂直租房场景的智能助手，核心交付物是三样：可核对的审查结论、可执行的谈判弹药、可验证的修订合同。不是通用聊天机器人（不闲聊），也不是全自动 Agent（不替用户签字谈判）。

Q36：一句话塞了审查、证据、法条、话术、修订这么多卖点，用户记得住吗？

  一句话是分层的：对用户只有一句「签约前把坑找出来、谈掉、确认改好」，其余都是支撑点不是广告词。标准版那句话是给面试官/合作方讲定位用的，用户利益版才是对外的传播口径——定位一句话和传播一句话是两个东西，不能混用。

Q37：说「AI 审查」用户会预期 100% 准，出错了就是过度承诺，怎么办？

  措辞刻意控制承诺边界：说「帮你找出风险、附证据和法条你自己核对」，不说「保证不被坑」；动词用「帮你」而不是「替你」，交付物用「可核对」而不是「正确」。产品内长期明示「提供协商依据，不构成法律意见」。一句话介绍里承诺的边界，和产品兜底的边界是对齐的。

Q38：「第一次租房的应届生」人群太窄，一句话就把市场说小了？

  定位一句话不是广告 slogan，作用是收口而不是引流：窄人群是 MVP 的聚焦选择（需求同质、必经节点、无经验可标准化），产品能力对换租人群、商租场景泛化几乎零成本。先窄后宽是节奏判断：先在一个窄到能穿透的人群里验证「用时必到」，再谈扩张。

十一、下一步迭代规划：如果这个产品继续迭代，你的下一步规划是什么？（按迭代方法论推导）

回答思路：不报功能愿望清单，先讲清「我用什么机制决定下一步做什么」——「数据 + 用户反馈」双轮驱动的迭代闭环：数据告诉你「发生了什么」，用户反馈告诉你「为什么」，方案上线后再用数据验证。然后用这套机制推导出当下已经排定的第一轮迭代内容。

总回答：我的下一步规划 = 一套迭代机制 + 第一轮已排定的迭代内容。固定闭环七步：看数据定位问题 → 看反馈找原因 → 定方案 → 排优先级 → 小版本快速上线 → 再看数据验证 → 循环。机制保证「下一步做什么」永远有依据；内容是我按这套机制从现状推出来的第一轮答案。

Q39：你说要数据驱动，可产品刚上线没多少数据，这套闭环怎么启动？

  分三步启动：①小样本 3-5 人陪同测试的观察记录当第一轮「定性数据」输入——数据不够时反馈补位；②埋点先立口径（六级漏斗、采纳率定义）再攒数据，避免「先采后定义」导致口径对不齐；③第一轮迭代本身就是装仪表盘——闭环从「装仪表盘」这件事开始转起来。诚实承认没数据，比编一套漂亮数据更可信。

Q40：用户偏好记忆和你的隐私原则冲突吗？

  不冲突，前提是记忆的对象是「偏好」而不是「合同」：记住的是「用户首租、关注押金、预算紧」，不存合同全文与审查结果；实现上本地优先、明文可查看、一键删除，和「仅本地模式」是同一套控制权哲学。隐私不是靠不加功能，而是每加一个功能都过一遍控制权检查。

Q41：建议执行出了错谁负责？你不怕自主化出事故？

  分级放开的本质是把错误成本封顶：话术是「拟好待发」，发送动作与对象永远由用户确认——错误最多停在草稿箱；真正高风险的动作（签合同、付钱）不进自动化范围。这与第(4)问的定位一致：不是能力做不到全自动，是场景不该全自动。

Q42：freemium 会不会把最好的功能锁起来、反而伤信任？

  免费层保留的是「可信底线」：审查+证据+法条完整可用——这恰恰是口碑来源；付费加深的是「使用密度」（军师次数、导出、对比），不封闭任何已经看到的风险结论。原则：不卖「安全感」（那是把用户当人质），卖「深度使用」。

Q43：为什么不趁势铺开劳动合同、购车合同，把盘子做大？

  先窄后宽（与 Q38 同源）：垂直壁垒是 55 类租房规则+本地法条库+谈判流程沉淀，铺新场景等于每个场景重建壁垒；且首租应届生是「用时必到」最强的场景，先穿透再复制方法论。泛化的正确姿势是「架构可复制」，而不是「同时开做」。

Q44：如果大厂下场做一模一样的事呢？

  参照 Q17 的发动机/整车论：大模型能力是发动机，我沉淀的是租客视角规则库、法条库、谈判三态流程和真实 badcase 迭代记录——这些是运营资产不是技术资产，复制需要时间而不只是钱；且大厂做通用，我做窄人群穿透，节奏上先建立「签约前，用签约有数」的心智。

Q45：低频工具留存天然难看，你这个产品怎么定义「留存健康」？

  不拿日活为难自己：按方法论，一周用不了几次的产品看周留存/月留存。签约有数再叠加「事件触发留存」——用户或其同学进入下一个签约场景时是否回来；再加上 NPS（愿不愿推荐给同学）当前置信号。DAU 对这个产品是会带偏决策的指标，刻意不设目标。

Q46：用户提的功能建议你都听吗？会不会被带偏？

  建议 ≠ 需求，用户反馈只是需求来源之一。按定位过滤三判据：是否服务「首租应届生签约前」场景、是否越过 human-in-the-loop 边界、成本收益是否成立。例子：「自动发微信给房东」越过边界 → 改造成「拟好待发、用户确认」；「支持商用租赁合同」场景漂移 → 进 P3 观察。听得进用户，但过滤靠定位。

Q47：小版本快速上线，和你 55 类规则回归门禁的测试完备性矛盾吗？

  不矛盾——小版本指的是功能切片，不是质量切片。每周上线的每个小版本，规则层都有 171 项回归测试守门（黄金集+零风险对照组），AI 层有证据逐字绑定约束影响面。快跑的是范围，不降的是下限；这恰恰是「规则保下限」架构在迭代节奏上的红利。

Q48：数据指标和用户反馈打架时听谁的？

  它们不是竞争关系是分工：数据定位问题、反馈解释原因。例：功能完成率高但留存低——数据说「用户都走完了」，反馈说「走完一次没有再来的理由」，合起来结论是「单次价值成立、回访价值缺失」，对策才是补高频场景/偏好记忆而不是修流程。只看数据会开错药，只听反馈会以偏概全，双轮缺一不可。
