# 签前有数 · 真实合同评测集标注规格 v1.0

日期：2026-11-17
适用范围：`app/scripts/verify/` 下所有评测脚本（现有 `eval-defect-library.mjs` / `eval-quality.mjs`）
定位：把「审查准不准」从主观感觉变成**可复算、可回归、可放进作品集**的一组数

---

## 0. 先说边界：这份规格解决什么、不解决什么

| | 内容 |
|---|---|
| **解决** | 有没有一套**真实合同**的人工标注，能算出召回率、误报率、分档准确率，且每次改 prompt / 换模型都能复算同一个数 |
| **不解决** | 不证明法律正确性（标注员是产品标注员，不是律师）；不证明用户价值（采纳率/省钱是另一套埋点）；不替代 A 档法条的人工复核 |
| **为什么现在做** | 现有两套评测集——45 条缺陷库、28 份整份合同——**全部是自造变体 + 植入式**：先写缺陷条款，再植入示范文本底板。规则照着它写，它自然全中。这是过拟合，能证明「没改坏」，不能证明「对真实合同准」。真实合同的标注条数目前是 **0**。 |

> 数字来源：`app/scripts/verify/eval-defect-library.mjs`（45 条 / 28 份 / 四指标口径）；`deliverables/合同审查效果评估与稳定性诊断_20261116.md`（自造变体、召回 37–46% vs 裸模型 79–86%、证据回查 100%）。所有引用数字均可追到这两处。

## 1. 现状盘点（先把家底盘清楚，避免重复造轮子）

| 资产 | 位置 | 用途 | 局限 |
|---|---|---|---|

## 2. 口径先行：三个必须先拆开的歧义

这三个坑不先填，标注出来的数据没法用。

### 2.1 `note` 一词两义 —— 最危险

- 缺陷库里 `expected_level: 'note'` = **不该报**（合规条款，报了算误报）。判分脚本里 `should_report = ['must','check'].includes(expected_level)`，note 被排除在应报项之外。
- 产品 UI 里 `note` = **仅提醒**（会渲染成一张卡，只是最低档）。`riskModel.js` 的三级是 must / check / note。

**规则**：标注集**必须**把「要不要报」和「报的话归哪档」拆成两个独立字段——`should_report`（bool）与 `expected_level`（must/check/note）。禁止用 level 推断是否应报。

### 2.2 标注单元 = 风险语义点，不是句子，也不是模型输出条数

- 一个**独立不利机制**算一点，哪怕跨两三句；
- 一句话里含两个独立机制（如「逾期 5%/日」+「逾期 3 日换锁且押金不退」）算两点；
- 同一机制换几种说法重复出现，合并为一点，evidence 取最清晰的一处。

理由：现有诊断显示模型输出条数会漂移（5/5/5 vs 5/6/4）但风险语义集合基本稳定。按「条数」标注会把这个稳定性问题直接污染进 gold set。

### 2.3 `A/B 档` 不是 `must/check` 的另一套说法

- `annotation_confidence: A` = 法规或标准卡写得明确，**进主评分**；
- `annotation_confidence: B` = 产品阈值灰区、标注员自己也有争议，**只测一致性，不计对错**。

现有脚本已经是这个口径（A 档单列主评分，B 档只测一致性）。B 档存在意义是：诚实承认有些条款「说不清是不是风险」，不要硬塞进对错统计里制造假精度。

## 3. 字段设计

### 3.1 合同级字段（一份真实合同 = 一条 contract 记录）

| 字段 | 类型 | 取值 | 必填 | 说明 |
|---|---|---|---|---|
| `contract_id` | string | `REAL-001` 起 | ✓ | 唯一编号，不与植入式 `DEF/NEG` 混用 |
| `source_channel` | enum | 中介模板 / 房东自制 / 平台电子 / 个人转让 | ✓ | 控制来源分布，避免全是中介模板 |
| `city` | string | 武汉为主 | ✓ | 地方法规核对口径 |
| `text_sha256` | string | 64 位十六进制 | ✓ | 正文指纹，锁版本防篡改 |
| `word_count` | int | — | ✓ | 与可读性分级挂钩 |
| `format_original` | enum | pdf / docx / img / txt | ✓ | 测跨格式一致性 |
| `redaction_log` | array | `[{"field":"姓名","method":"占位"}]` | ✓ | 脱敏了哪些字段、怎么脱的 |
| `annotator_a` / `annotator_b` | string | 姓名或代号 | ✓ | 双人独立标注 |
| `adjudicator` | string | — | 分歧时必填 | 仲裁人 |
| `status` | enum | drafting / adjudicated / frozen | ✓ | 只有 frozen 才进评测 |

### 3.2 风险点级字段（对齐现有缺陷库，可直连判分脚本）

| 字段 | 类型 | 取值 | 必填 | 对接现有脚本 |
|---|---|---|---|---|
| `point_id` | string | `REAL-001-P01` | ✓ | 新增（缺陷库是 case_id） |
| `contract_id` | string | — | ✓ | 新增，回挂合同 |
| `playbook_id` | enum | 9 张卡 id 或 `out_of_scope` | ✓ | = 现有 `playbook_id` |
| `finding_type` | enum | `explicit_disadvantage` / `missing_term` / `needs_review` | ✓ | = 现有 label 语义 |
| `should_report` | bool | true / false | ✓ | **新增**（见 2.1，替代用 level 推断） |
| `expected_level` | enum | must / check / note | ✓ | = 现有 `expected_level`，但语义改为「报的话归哪档」 |
| `severity_raw` | enum | high / medium / low | ○ | 新增，供 level 映射复算 |
| `evidence_quote` | string | 正文连续子串 | ✓ | ≈ 现有 `clause_text`，但**要求逐字可回查** |
| `evidence_location` | object | `{article, line}` | ✓ | ≈ 现有 `locationOf` 输出 |
| `expected_facts` | object | 数字/期限/机制锚点 | ○ | = 现有 `expected_facts` |
| `harm_mechanism` | string | 一句人话 | ✓ | ≈ 现有 `reason` 的前半段 |
| `annotation_confidence` | enum | A / B | ✓ | = 现有 `annotation_confidence` |
| `basis` | string | 法条号或产品阈值 | ✓ | = 现有 `basis` |
| `counter_signal_hit` | bool | — | ○ | 新增，命中反例信号 → 应判 `should_report=false` |
| `disagreement` | bool | — | ✓ | 双人是否不一致，驱动仲裁 |

### 3.3 负例标注（测误报，和正例同等重要）

每份合同除「应报点」外，**必须**同时标注至少 1 条「保护性条款」作为负例：

- `should_report: false`
- `expected_level: note`
- `counter_signal_hit: true`
- 例：「交接后 7 个工作日内退还押金，扣款须有照片、清单和票据」——标准卡里的合规写法，模型报成 must 就是误报。

理由：现有脚本的误报主口径就是「note 变体被报成 must/check」+「引文不在原文」。真实集要有自己的负例，不能靠植入式的 note 变体。

## 4. 标注规范（标注员操作手册）

### 4.1 三级的可操作判定式

不用形容词，用能不能回答的问题：

| 档 | 判定式（满足任一） | 例子（来自 `sample-landlord-self-drafted.txt`） |
|---|---|---|
| **must** | 签字后直接产生确定金钱损失 / 押金没收 / 单方涨价 / 无条件换锁 / 丧失法定权利；或 `severity_raw=high` 且证据确定 | 「逾期超过 3 日，甲方有权解除合同并更换门锁收回房屋，已收押金不予退还」 |
| **check** | 条件或程序明显不利，但要结合实际执行才知是否致损；或 high 但证据只能靠 AI 推断；或 medium 且 finding_type 属 `explicit_disadvantage`/`missing_term` | 「押金在甲方完成房屋验收、结清水电等费用后的 45 个工作日内退还」（期限过长，非没收） |
| **note** | 正常条款中值得留意之处；或 `needs_review` 待核对 | 「月租金 2800 元，每月 1 日前支付」（正常，仅记录） |

定档逻辑与 `riskModel.js#levelFromSeverity` 保持一致；标注时同时记录 `severity_raw`，脚本可复算映射是否一致。

### 4.2 `finding_type` 怎么判

- `explicit_disadvantage`：原文有明确不利机制（要付多少钱、要失去什么权利）；
- `missing_term`：本该约定的保护条款缺失（如没写押金返还时间）；
- `needs_review`：有描述但边界不清，需看上下文，不能下结论。

### 4.3 证据逐字规则（硬约束）

`evidence_quote` 必须是合同正文的**连续子串**，一字不改。标注时复制粘贴，禁止概括、禁止改写、禁止跨段拼接。校验：`evidence_quote` 去空白后必须能在正文里 `indexOf` 命中，否则该点作废重标。

理由：判分脚本已有「引文不可回查率」指标；标注集自己先做到，才能公平要求模型。

### 4.4 卡外风险必须留口子

真实合同一定会出现 9 张卡覆盖不到的风险（管辖约定、个人信息、送达方式、口头约定效力）。标 `playbook_id: out_of_scope`，**不要硬塞进最接近的卡**。这批数据是后续扩卡的依据，硬塞会把「模型没报标准卡」误判成漏报。

### 4.5 脱敏规则

入库前删除/替换：姓名、手机号、身份证号、银行账号、精确到门牌号的地址、可定位个人的其他信息。用 `【脱敏-字段】` 占位。脱敏后重算 `text_sha256`，脱敏日志留档。

### 4.6 来源分布控制（防过拟合的采样规则）

- 四种 `source_channel` 尽量均衡，每种 ≥ 5 份；
- 同一房东/中介的模板去重；
- 建议规模：**20–30 份真实合同**，风险点 60–120 条（10 类分布见标准卡 + 卡外）；
- 宁可少而干净，不要为凑数放低一致性门槛。

## 5. 标注流程与一致性控制

```
脱敏入库 → 标注培训(用本文档 + 3 份练习合同) → 双人独立标注(互不可见)
   → 一致性计算 → 分歧仲裁 → 冻结版本 → 接入判分脚本 → 改 prompt/换模型后回归
```

**一致性门槛**（行业通行建议值，**非本项目实测数字**，需按实际标注人力校准）：

| 指标 | 建议阈值 | 不达标怎么办 |
|---|---|---|
| 是否应报（`should_report`）Cohen's kappa | ≥ 0.75 | 回看分歧案例，细化 4.1/4.2 的判定式后重标 |
| 分档（`expected_level`）一致率 | ≥ 0.80 | 把 B 档灰区案例单独拎出来讨论 |
| 证据逐字可回查率 | = 100% | 逐条作废重标，无例外 |

仲裁规则：分歧点由 `adjudicator` 裁定，裁定理由写入 `harm_mechanism`；B 档分歧保留双方意见，不强求一致，只在一致性样本里统计。

## 7. 怎么接进现有评测脚本（可复算，不造平行标准）

新建 `app/scripts/verify/eval-real-contracts.mjs`，**复用** `eval-defect-library.mjs` 的现成函数，只替换输入来源和判定入口：

| 复用 | 改动 |
|---|---|
| `bigramJaccard()` 证据重叠匹配 | `matchFinding()` 里 `implanted_text` → 标注点的 `evidence_quote` |
| `factCoverage()` 数字锚点覆盖 | 入参从 `case.expected_facts` → 标注点同名字段 |
| 四指标 `agg()` 汇总口径 | `should_report` 从 `expected_level∈{must,check}` 改为直接读 bool 字段 |
| A 档主评分 / B 档只测一致性 | 不变 |
| 误报口径 | note 变体 → 标注的负例点（`should_report=false`）；引文不可回查率照旧 |

新增两个真实集专属指标：
- **卡外召回**：`out_of_scope` 点被模型报出的比例（看覆盖盲区）；
- **格式一致性**：同一合同不同格式（txt/pdf/img）之间召回差异。

回归门槛（改 prompt 或换模型后）：A 档召回不下降、误报率不上升、证据回查率保持 100%。三条全过才合入。

## 9. 作品集 / 面试怎么讲

**一句话**：
> 发现现有评测集全是自造变体、存在过拟合，于是建立真实合同人工标注集：定义 15 个字段、双人独立标注 + kappa 一致性门槛，把「要不要报」与「报哪档」拆开以消除口径歧义，并让同一套脚本可复算召回/误报/分档。

**面试官追问「为什么这么做」**：
- 为什么双人 + kappa：单个人的标注就是偏见，一致性低说明标准没写清，不是标注员笨；
- 为什么要 out_of_scope：9 张卡是产品当时覆盖面，真实合同一定有卡外风险，硬塞会让「漏报」和「没定义」混为一谈；
- 为什么要负例：只标正例会鼓励模型「宁可多报」，误报率就测不出来；
- 为什么 A/B 分档：诚实承认灰色地带，比把所有条款硬判对错更接近法律现实。

**这段经历体现的 PM 能力**：定义评估口径 → 发现过拟合 → 建可复算基线 → 用一致性指标驱动规范迭代。这是「评测驱动迭代」的完整闭环，不是调 prompt。

## 10. 立即可做的第一步

1. 拿 `sample-landlord-self-drafted.txt` 按第 6 节格式补全双人标注（这份已经有了单人的示范标注）；
2. 再找 3–5 份真实脱敏合同，用同一套字段标，跑一次 kappa，看规范哪里写不清；
3. 规范稳定后再扩到 20–30 份，冻结 v1.0，接判分脚本。

每扩一批，就多一格真实合同的证据。这件事没有捷径，但每一格都能写进作品集。
